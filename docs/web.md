# The web page

The web page is the easiest way to use afk. From a browser, on your phone or your desktop, you can plan a new project by chatting with the planning agent, approve the plan, watch the daemon build it task by task, and answer the questions it saves for you. It is served by `afk daemon`, so it is there whenever the daemon runs.

The one thing it does not do is show an agent's terminal. To watch an agent work or type into it, use the terminal dashboard ([dashboard.md](dashboard.md)).

## A project from start to finish

1. **Sign in.** Open the page's address in your browser (`afk install` shows it on its last screen) and type the password you set with `afk web password`. The browser remembers you for 180 days. Every detail is under [Reference](#reference) below.
2. **Plan a new project.** Press **Plan a new project** in the top bar. Type a name, such as `shop`, to make a new folder under your project location, or the full path of a folder you already have. Press **Continue**, check the card, and press **Start planning**.
3. **Answer the planning agent.** You land in the planning chat. The agent asks what you want to build and asks its questions in rounds. Each question shows its options as buttons, with the one it recommends first. Leave whenever you like; when it needs you again you get a notification (if you set up ntfy) and the chat is where you left it.
4. **Approve the plan.** When the plan is written, the project screen says it is waiting for you. Open the plan, read it, and press **Approve the plan…**. That is your "go".
5. **Let it build.** The daemon starts the first ready task within a few seconds. The project screen shows what is running, how far along the plan is, and how much of your usage is spent. Each finished task becomes a pull request that is merged when its checks pass.
6. **Answer the inbox.** When a task needs something only you can give (a key, an account, a choice), it stops and puts an item in the project's inbox. Answer it on the page and the task carries on.

The Pause and Resume buttons hold and release the daemon. A pause stops new tasks from starting; a task that is already running carries on and finishes.

## Reference

`afk daemon` can also serve a small web page, so you can see what it is doing and unblock it from a phone. It shows each project's current task, the usage reading and the inbox, lets you answer an inbox item, has Pause and Resume buttons, plans a new project in a folder you name, starts extend, amend or reconcile on a project's plan, and acts on a project's sessions: it starts a new autonomous session, restarts a stopped or stuck one, sets a session's label, and cleans a finished one up. Each session action asks you to confirm first. It also approves a new plan that is waiting for review, behind a confirm too (see `/p/<project>/plan` below). It is off until you set a password with `afk web password`.

**Turn it on.** Run `afk web password` in a terminal on the machine afk runs on. It asks for the password twice without showing it; it must be at least 8 characters, and a short or mismatched one saves nothing. afk saves a salted hash of the password in its state folder, in `web-password.json` (readable only by you). The password itself is never saved, and `config.toml` never holds it. Then restart `afk daemon`, which turns the page on when it starts; its log then says `web page: listening on http://127.0.0.1:4253`. Without a password the log says the page is off, no port is opened, and the daemon runs as it did before. A password you change while the page is on takes effect at once, and it signs every browser out. A leftover `token` line in `[web]` is not used any more: the daemon logs one line saying so and ignores it, so you can delete the line.

**Where it listens.** `bind` defaults to `127.0.0.1:4253`, which only this machine can reach. If you bind an address other machines can reach (`0.0.0.0:4253`, `:4253`, a LAN address or any name other than `localhost`), a password is required: with none, `afk daemon` exits 1 naming `web.bind` in `config.toml` and telling you to run `afk web password`. A password file that cannot be read counts as none. If the port is taken, it exits 1 saying so.

**Plain HTTP.** The page speaks plain HTTP and has no TLS of its own. It is meant to sit behind Tailscale or a reverse proxy; do not put it on the open internet as it is.

**Sign in once.** Open the page in your browser. A page you have not signed in to shows a sign-in form: type the password and press **Sign in**. A right password leaves a cookie in the browser that lasts 180 days, so after that the page opens without asking. A wrong password shows the form again with a line under the field. Five wrong passwords in a row pause sign-in for one minute, for the whole page; a try made during the pause is refused and does not make the pause longer. **Sign out** is on both bars, the desktop top bar and the phone bar, and it signs this browser out only. Setting a new password signs every browser out. A tab that was open across a password change shows Offline until you reload it. A `Secure` cookie (an `https://` `public_url`) is dropped by the browser over plain HTTP, so over an `http://` address the form just comes back; use the `https://` address you set in `public_url`. Sign-in sends you back to the page you asked for, and only to a page on this site. An `/api` address with no cookie answers 401 with a short JSON message instead of the form.

**What each page shows.**

- `/` — the all-projects screen. Its heading says how many projects need you ("2 projects need you", or "Nothing needs you"). **Needs you** comes first and lists the projects that wait on the owner; **Everything else** lists the rest, in the same order the dashboard uses. Each row shows the project's state as a word (Building, Waiting on you, Paused, Line stopped, Held for usage, Nothing ready, Finished, Gone, Can't read, No plan), the task being worked on and its phase, or in plain words why nothing is running, how many tasks are done as a bar, and how many inbox items are open and how many hold a task up. A plan waiting for approval is its own row, "Plan waiting for approval", and links to the plan. On a desktop-width screen the first row (the one that needs you most) is also shown on the right, with its details and a link to its page; on a phone the list is the whole page. The usage reading is on this page too. The page updates itself while it is open (see *Live updates*). It has an **Add a project** button in the top bar and an **Add an existing project** button and a **Remove a project** button in the footer, which open the add and remove pages below. After one of those changes, a notice on the page says it was added or removed and that it shows (or goes) within a few seconds: the daemon re-reads its project list on its next pass, and the page shows the list as the daemon last read it. The notice goes away once the list shows the change, or after ten minutes.
- `/projects/add` — **Add an existing project**. It asks for **Folder**, the full path of a project's folder or a path starting with `~/`, and an optional **Name** that defaults to the folder's own name. **Add project** adds the folder to the daemon's list, as `afk project add` does, and the folder must be a git repository. A folder that is already listed is not an error: the page says so and changes nothing. A refusal (such as an empty folder, or a name already taken) keeps the form open with what you typed and says why, and nothing is written.
- `/projects/remove` — **Remove a project**. It lists the projects on the daemon's list as a choice list, with each folder beside its name. Pick one and **Remove…** opens a confirm sheet that names the project and its folder. **Remove** takes the project off the list, as `afk project remove` does; the folder, its plan and its sessions are left alone. **Keep it** closes the sheet and changes nothing.
- `/projects/remove/confirm?name=<name>` — the same confirm for a browser with no JavaScript, with the same words and the same **Remove** and **Keep it** choices. A name that is not on the daemon's list gets a plain sentence and nothing changes.
- `/p/<project>` — the Project screen for one project. A state card shows the daemon's state as a badge, a headline in words (for example, how many inbox questions hold up a task), one line of detail, the progress bar, and the one next action: answer the inbox, resume a paused or stopped project, or read and approve a waiting plan. Below it are **Running now** (the tasks being worked on, with their session; each row links to that session's screen), the **Pause project** or **Resume project** button, a **Plan** row that links to the plan and says where the planning is in one line (the plan line, for example "plan: plan waiting for your approval"), a short list of **Inbox**, **Tasks**, **Sessions**, **Plan** and **Usage** (the inbox with its open count, Tasks as "N of M" done, the same count as the progress bar, and Sessions with how many the project has), and the project's **Folder** and **Repository**. Below the list, the **Change the plan** section has three rows, **Extend**, **Amend** and **Reconcile**, each with one line on what it does; they start a planning session that changes the plan (see the change page below). While a planning session is open the section says so instead and links to its chat, and a project with no plan gets one sentence and no rows. The card, Running now, the button and the list update by themselves (see *Live updates*).
- `/p/<project>/inbox` — the project's inbox as its own screen. A notice says how many open items hold a task up. Open items are listed, blocking ones first, each with its task, its title, what kind of item it is and how long ago it was raised. Answered items sit under "Answered (N)". When nothing is open the screen says "Nothing needs you". After an answer you come back here, and a toast says what happened: "Answer sent.", "Answer sent. T3.4 is ready again." (only when the task was parked and no other open item holds it), or "Marked as done." for a task only you can do.
- `/p/<project>/inbox/<id>` — one inbox item, with a Back link to the inbox. If it is open, the form takes your answer. The options are buttons, the recommended one first and marked "Recommended"; "Or write your own" takes text, and typed text wins over a chosen option. An owner task, one only you can do, shows its instruction and a single **Mark as done** button, which records the answer `done`. The answer is stored with the channel `web` (the item then reads "Given ... through web"), and the daemon un-parks the task on its next pass, exactly as after `afk inbox answer`. A second answer to the same item is refused and the first is kept. With JavaScript on, choosing an option only marks it, and **Send answer** stays disabled until something is chosen or written; sending goes back to the inbox without a reload. With JavaScript off, a tap on an option sends that option at once and the page reloads as before.
- `/p/<project>/tasks` — the project's tasks, as `afk tasks` lists them. Open, Done and All sit at the top (`?show=open`, `?show=done`, `?show=all`); Open is the default, and any other value also shows Open. Each milestone of the plan is a section with its heading and a "N of M done" count that does not change when you switch filters. A row shows the task's id, its title and its status as a word (a superseded task says which tasks replace it). A task that is neither done nor superseded and still waits for others has a "Waits for T3.4, T3.5" line. Tasks above the first milestone heading sit under a plain "Tasks" heading, and an empty filter says why ("No open tasks", "Nothing done yet"). The list updates by itself while it is open. If the plan or the ledger cannot be read, the page says why in a notice instead of the list.
- `/p/<project>/tasks/<id>` — one task's screen, with a Back link to the list. It shows the task's status as a word, one plain line on why the task is in that state, and what it depends on. The **Tokens** card shows the tokens the task used: a bar split by phase with a legend underneath, and a table by role. A task with no record yet says "No tokens recorded for this task yet." A record that cannot be read says so on the card. The **Set status…** button opens the status sheet described under "Set a task's status" below. An id that is not in the plan answers 404 with a plain sentence. If the session the ledger names is still found, the screen has an **Open its session** link to that session's screen; a session that has been cleaned up gets no link.
- `/p/<project>/sessions` — the project's sessions, every session discovery finds for the project, in the dashboard's order. Each row shows the label (or the session's name), its phase as a badge, a progress bar when it has a work plan, a **Waits for you** badge when it is waiting for an answer, a **Stopped** badge when its host is not running, and its review verdict (**Approved** or **Changes asked**) once it has one. A row that is not an ordinary session says what it is in a line under it, with its own badge: **One-off** (a session with no plan, only a terminal), **Planning** (the planning session for the project's master plan), **Status unknown** (its `status.json` could not be read, with the reason) or **Problem** (a worktree that is not a session, with what is wrong). A running host whose agent has gone quiet says so in a line. Each row shows the first eight characters of the session's id, and the whole id is in its tooltip. A project with no sessions says "No sessions yet". Each row links to its session's screen, except the **Planning** row, which links to the planning chat. The list updates by itself while it is open. Above the list, **Start a new autonomous session…** opens a short form (a name and a description) that starts a new session; see *Session actions* below.
- `/p/<project>/sessions/<name>` — one session's overview, with a Back link to the list. A state card shows the phase as a badge with the loop count, when the session started and when it was last updated, its label, branch, folder and host (running, not running, or running but its agent has gone quiet). A **Summary** says in sentences what the session is doing: its phase, whether it waits for you, its work-plan progress, the review verdict for each check, whether its host is running, and why its status is unknown when it is. The page cannot open the session's terminal, so the screen says to open it from `afk dash` or with `afk attach <name>`. A planning session's screen also links to the planning chat. Its **Actions** rows are **Restart**, **Label** and **Clean**, and each opens a confirm sheet (see *Session actions* below). It does not show git diff stats or the tail of the issues file. A name that is not in the project answers 404 with a plain sentence saying it may have been cleaned up. The state card updates by itself while the page is open.
- `/p/<project>/plan` — the project's master plan, drawn as a page. At the top is the plan line (the planning session's mode, phase and what it waits for, in the same words as `afk dash`), then the **checker card**: a badge, the counts from `afk plan lint --summary`, and the checker's findings with the errors first, each worded as `afk plan lint` words it. A finding that names a task links to that task's heading in the plan below; one that names no task shows its file and line as plain text. Then come the open questions and the plan's own text, with each task heading linkable (`#T5.7`). **Approve the plan…** is shown only for a new plan at review with no checker errors. It opens a confirm that names the project, the plan's path and the counts, with **Not yet** focused and **Approve and start** as the other button; with JavaScript off the same confirm is its own page. Approving runs the same steps as `afk plan approve`, and the result page says what was done, what was refused, or which step failed and what to run. A plan with errors shows a red notice that says how many errors to fix, and no approve button; a plan that is not at review says why it cannot be approved. A plan waiting for approval is shown here even though its project is not in `config.toml` yet, and it can be approved the same way; the home page `/` lists it under Needs you as "Plan waiting for approval". If the plan cannot be read, the page says which file and why.
- `/p/<project>/plan/change?mode=extend|amend|reconcile` — the change page, reached from a Change the plan row or button. Extend shows a confirm card that names the project and says a planning agent reads the plan and asks what to add. Amend asks for the sentence that should change ("What should change?"), and Reconcile asks for a document path inside the project, such as `docs/design-system.md`. The next step is a card showing what will start and the text, with **Start planning** and **Cancel**. Nothing starts until **Start planning** is pressed; the page has no `--yes`, so amend always asks. A refusal redraws this page with the reason above the form, in the command's own words and with the text you typed kept. When a planning session is already open the page says so and links to its chat; with no plan it says there is no plan to change yet. An unknown mode answers 400 with a sentence saying so. A start goes straight to the planning chat with a short notice on it. It works with JavaScript off, because the confirm is a page of its own.
- `/plan/new` — Plan a new project, reached from the **Plan a new project** link on the all-projects screen and in the top bar. Its **Where** field takes the full path of a folder, such as `~/code/shop` (`~` works), or a project name. A name makes a new folder under the `project location` in your owner profile (set it with `afk profile set "project location" ~/code`), so `shop` becomes `~/code/shop`. **Continue** shows a confirm card with the full path and what the folder is: an existing git repository, an existing folder that planning will turn into one, or, for a name, a new empty folder that afk will create and make into a git repository. Nothing starts until you press **Start planning**, which makes the folder and its repository (for a name) and then takes you to the planning chat. After a name's folder is made, and when `gh` is ready, the page asks **Create a private GitHub repository for it?** and names the repository `<account>/<name>`, with your existing `gh` login as the account. The choices are **Yes, create** it as a private repository, and **No, I'll add one later**, which is checked by default. Yes makes exactly one private repository and sets it as the folder's `origin`; nothing is pushed. No makes nothing. Planning then starts either way: a repository that could not be made (its name is already taken, `gh` failed, or it was made but could not be set as `origin`) is shown with its reason, and planning starts all the same. When `gh` is missing, not logged in, or afk cannot name your account, the question is not asked: planning starts and the page says why and what to run. The question is asked every time and never remembered, and only for a folder the page has just made. A folder that existed before the form is never offered a repository, and an answer that comes more than an hour later, or a second time, makes nothing. It refuses, in a sentence, a path that is not a folder, a folder that is not there (it is named in the sentence), a folder that already has a plan (use Change the plan on its project to extend or amend it), a name with characters other than letters, digits, `.`, `_` and `-`, a name when there is no project location (the sentence says how to set one, or to type a full path instead) and a blank or overlong path. A name whose folder already exists is offered as that folder, with its existing card, and creates nothing. A refusal starts nothing and creates nothing. If a planning session is already open in the folder, the card says so and Start planning takes you back to it. A project started here stays on the all-projects screen, marked **Being planned**, until you approve its plan or its planning session is gone. afk keeps that list in `being-planned.json` in its state folder. Nothing is written to `config.toml`. The page creates a folder only for a name, directly under the project location, and only after the confirm; it never creates the project location itself. If making the repository fails part-way, the folder stays on disk, nothing is removed, and no planning session starts. It works with JavaScript off. The server asks for the confirm too: a POST without it answers 400 and starts nothing.
- `/p/<project>/plan/chat` — the planning chat: the conversation with the project's open planning session, read as messages. The agent's messages are drawn as formatted text, and yours appear as you typed them. When the agent asks a question, each option is a button, with the recommended one first and marked "Recommended". "Or answer in your own words" takes your own answer to one single-select question, and the reply box stays off until the question is answered. Otherwise the reply box is at the foot of the page; it is disabled while the agent works, and a line says so. With no planning session open, the page says "No planning session" and has no reply box; it offers the same three buttons as the project screen's Change the plan section (Extend, Amend and Reconcile), and says there is no plan to change yet when the project has no plan. A refused reply says why in plain words and keeps what you typed. The page never shows the terminal; open the planning session from `afk dash` or with `afk attach` to see it. The reply is an ordinary form, so it works with JavaScript off.
- `/usage` — the usage screen. A **What afk is doing** card shows the governor's decision as a badge, with the reason, when it wakes (if it is paused or held) and when it was decided. A **Usage windows** card has one meter per window: how full it is, and when it resets. Below them is a **Refresh usage** button and a note on what the five decisions mean (Run, Launch nothing new, Pause, Hold, Refuse). Pressing **Refresh usage** takes a fresh reading in the background, the same as `afk usage --refresh`. The button reads "Refreshing" while the reading runs, and the new numbers appear on the page without a reload; after a successful reading it reads "Checked just now" for a minute. Only one reading runs at a time, so a second press while one is running does nothing and the page says so. A reading that fails shows a plain sentence saying why, with the reading that worked before still on the page, marked as the last one that worked. Nothing takes a reading on a timer, when the page opens, or when the live stream starts; only the button does.

**Set a task's status.** A task's screen has a **Set status…** button. It opens a sheet that offers every status the ledger takes (pending, running, shipping, parked, done, failed and superseded), with the task's current status checked. Pick one and the sheet says in one sentence what will change, for example "T3.4: failed → pending.", and what the build loop will then do with the task. If the task is running or shipping, the sheet first says that an agent is working on it now and that changing its status does not stop that agent. Choosing superseded asks for the ids of the tasks that replace it, such as T3.4a and T3.4b, and the sentence names them; it is refused without at least one id, and a task cannot replace itself. The sheet's safe button, "Leave it as it is", closes it and changes nothing. The action button names the status ("Mark pending"), and pressing it makes the change without a reload, after which the page shows the task with its new status. With JavaScript off, **Set status…** goes to `GET /p/<project>/tasks/<id>/status`, a two-step page. The first step lists the statuses as radio buttons with the current one marked, and a field for the replacing ids; the second step shows the same sentence as the sheet with a button to confirm. The server asks for the confirm too: a status POST that does not carry it changes nothing and answers 400 with "Nothing changed" and a sentence telling you to open the task and press Set status…. The sheet's button sends it, and so does the second step of the page. The change is written to the ledger by the same code as `afk ledger set`, with the same checks and the same words, so the file `afk tasks` reads is the one the page changes. Whatever the command would refuse, the page refuses with the command's words, for example an id that is not in the plan or an unknown status.

**Session actions.** The Sessions screens have four actions: starting a new autonomous session, Restart, Label and Clean. Each one changes nothing until you press its confirm button. Its sheet says in words what will happen, and its safe choice closes the sheet and changes nothing. A refusal is a plain sentence that says nothing was changed.

- **Start a new autonomous session…** starts a session as `afk new --autonomous` does: a new branch and worktree in the project, running on its own with the description as its work. It runs autonomously, not in unattended permission mode, so when its agent needs a permission it waits for you in `afk dash`. It needs a name (lower-case letters, digits and dashes, as `afk new` takes) and a description that is not blank and is at most 5000 characters. It refuses what `afk new` refuses, such as the reserved name `master-plan` or a name whose branch already exists.
- **Restart** is offered for a planned session only. A stopped session gets its host started again, and its agent resumes from its files. A running host whose agent has stopped answering is asked to restart that agent. A healthy running host is refused, because restart only replaces a stopped or stuck agent. Restart never touches a one-off session (restart that from `afk dash`), the planning session (open it with `afk plan`), or a session whose worktree has a problem. Asking a running host to restart takes its one connection, so an `afk attach` or a dashboard pane open in another terminal is dropped, as the confirm says.
- **Label** saves a new label for the session, which the list shows in place of its name. A label of more than 128 characters is refused, and so is a session whose worktree has a problem, since there is nowhere right to save it.
- **Clean** removes a session once it is done or failed. The page never forces a clean of a session in any other phase: it is refused with a sentence that points to `afk clean --force` or `afk dash`, as `afk clean` refuses it. If the session's host is still running, the clean stops it first, as `afk clean` does. The session's `.afk/<name>/` folder is archived and removed, and its worktree directory is removed too. A standalone session with no worktree of its own only loses its `.afk/<name>/` folder. The branch is always kept, because the page never deletes a branch. The page checks the phase you saw: if the session's phase has changed since the page showed it, the clean is refused and nothing is cleaned.

With JavaScript off, each action goes to a confirm page with the same words and the same choices: `GET /p/<project>/sessions/<name>/confirm/<action>` for Restart, Label and Clean, and `GET /p/<project>/sessions/new` for the new session. The server asks for the confirm too: an action POST that does not carry it changes nothing.

**Live updates.** An open page updates by itself within a few seconds of a change: a new inbox item, a task moving on, a pause, a new usage reading. The Sessions list and each session's screen update the same way, when a session's phase, loop count, work-plan progress, review verdict, label or host changes. The planning chat follows the conversation the same way: a new message or question appears on an open chat, and the question buttons and the reply box are swapped too. A swap waits while the cursor is in the reply box or the box holds text you typed, so a half-written reply is kept. The page opens a stream at `GET /events` (server-sent events, behind the same sign-in as every page) and swaps only the parts that changed, so what you are typing is never lost. The live indicator in the bar has three states. "Live" means the stream is up. "Working" means the stream is up and something on the page says afk is busy on it, such as a project's task in progress. "Can't reach afk, retrying" means the stream dropped; the page keeps what it had, reconnects on its own, and never turns into an error page. With JavaScript off, or behind a proxy that refuses event streams, nothing breaks: reload the page to see the latest. A proxy in front of the page must not buffer `text/event-stream` (for nginx, `proxy_buffering off`; the page already sends `X-Accel-Buffering: no`).

**Pause and resume.** The buttons do what [`afk pause` and `afk resume`](daemon.md#afk-pause-and-afk-resume--hold-and-release-the-daemon) do, including clearing a stopped line, and write to the decision log in the same way. Pressing Pause or Resume opens a confirm sheet (a dialog on the page) that says what will change and that nothing is deleted. Its safe choice, "Keep it running" or "Keep it paused", closes the sheet and changes nothing. The resume sheet says that afk starts the next ready task again and that a stopped line is cleared. With JavaScript off, the button goes to `GET /p/<project>/confirm/pause` (or `/confirm/resume`), a page with the same words and the same two choices. The server asks for the confirm too: a pause or resume POST that does not carry it changes nothing and answers 400 with a plain sentence. The sheet's own button sends it, and so does the confirm page. With JavaScript on, the change happens without a reload: the page is swapped for the new one. After a change, the project page shows a short notice that it happened ("Paused <project>. Nothing new will start." or "Resumed <project>."), which goes away on its own after five seconds.

**The JSON API.** Every page has a JSON twin under `/api`: `GET /api/`, `GET /api/usage`, `GET /api/p/<project>`, `GET /api/p/<project>/inbox`, `GET /api/p/<project>/inbox/<id>`, and `POST` to `/api/p/<project>/inbox/<id>/answer` (a body of `{"answer": "text"}` with `Content-Type: application/json`), `/api/p/<project>/pause` and `/api/p/<project>/resume`, `GET /api/p/<project>/plan` and `POST` to `/api/p/<project>/plan/approve` (see below), and `GET /api/p/<project>/plan/chat`, `POST /api/plan/new` (the twin of Plan a new project: a body of `{"path": "~/code/shop", "confirm": true}` with `Content-Type: application/json`, or the form fields `path` and `confirm=yes`; `path` takes a full path or a project name, the same as the Where field; without the confirm, or for a folder it refuses, it answers 400 with `{"error", "reason", "path"}` and starts nothing; on success it answers 200 with `path`, `root`, `project`, `outcome`, `chat`, `notice` and `created`, which is `true` when this call made the folder and its repository and `false` when the folder was already there; a name whose folder cannot be made answers 400 with reason `create_failed` and the `path` of the folder left on disk, and starts nothing and removes nothing). When the folder was made and `gh` is ready, the answer is 200 with outcome `github_question`, `path`, `created: true` and a `github` object holding `repo` (the name offered) and `question` (the question's words), and nothing is started yet. `POST /api/plan/new/github` answers that question with `{"path": "~/code/shop", "github": true, "confirm": true}` (`"github": false` for no) and `Content-Type: application/json`. A missing `github` means no. Like every POST it needs the confirm; without it the question stays open and nothing changes. The server acts only on a folder it has just made and is still waiting on: any other folder, a question already answered, or one more than an hour old answers 400 with reason `not_offered` and makes nothing, and the name of the repository is always the one offered, never one from the request. Yes makes the repository and sets `origin`; no makes none; nothing is pushed. Either way planning then starts, and the answer is 200 with `path`, `root`, `project`, `outcome`, `chat`, `notice`, `created` and a `github` object: with a question asked, its `outcome` is `created`, `declined`, `name_taken`, `failed` or `no_origin`, with `repo` and `text`; when `gh` was not ready, its `outcome` is `not_offered` with a `reason` and `text` instead. A start that is refused answers 400 with the same `github` object. `GET /api/` carries a `being_planned` list beside `projects` and `reviews` with the projects being planned, never null, `GET /api/p/<project>/tasks[?show=open|done|all]`, `GET /api/p/<project>/tasks/<id>`, and `POST` to `/api/p/<project>/tasks/<id>/status`. `POST /api/usage/refresh` starts one usage reading in the background, the same reading as the page's Refresh usage button. It needs no confirm, and it answers 202 with `{"outcome": "started"}`, or 200 with `{"outcome": "already"}` when a reading is already running (a second press does nothing). `GET /api/usage` then carries a `refresh` object with `state` (`idle`, `running`, `refreshed`, `failed` or `unsupported`), `text` (the sentence for a failed or unsupported reading) and `at` (when it started or finished), which is absent when there is no refresh to report; the other fields are as they were. The refresh POST is guarded like every POST: the sign-in cookie and the `Origin` check apply. The pause and resume POSTs need the confirm: a body of `{"confirm": true}` with `Content-Type: application/json`, or the form field `confirm=yes`. Without it they answer 400 with `{"error": ...}` and change nothing. `GET /api/p/<project>/tasks` lists the tasks under the same filter as the page (`show` is open by default, and any other value reads as open), and `GET /api/p/<project>/tasks/<id>` gives one task with its `unmet`, `why` and `tokens`. `GET /api/p/<project>/sessions` lists the project's sessions as the Sessions screen does, and `GET /api/p/<project>/sessions/<name>` gives one session's overview with the same facts. The two GETs only read. The four session actions are POSTs, and each needs the confirm: `POST /api/p/<project>/sessions` starts a new autonomous session with `{"name": "fix-login", "description": "Fix the login form", "confirm": true}`; `POST /api/p/{project}/sessions/{name}/clean` takes `{"phase": "done", "confirm": true}`, where `phase` is the phase the caller last saw (`""` for a one-off, or a session whose status cannot be read); `POST /api/p/{project}/sessions/{name}/restart` takes `{"confirm": true}`; and `POST /api/p/{project}/sessions/{name}/label` takes `{"label": "Login work", "confirm": true}`. Each takes `Content-Type: application/json`. Without the confirm a POST answers 400 with `{"error": ...}` and changes nothing. With it, every answer has the shape `{"project", "session", "result": {"outcome", "text"}}`: `done` answers 200, `refused` (nothing was changed) answers 400, and `failed` (the attempt went wrong) answers 500. `text` is the sentence the page shows, and the API refuses exactly what the page refuses. Each session has `name`, `label`, `kind` (`session`, `one_off`, `planning`, `status_unknown` or `problem`), `phase`, `waits_for_you`, `awaiting_input`, `loop_count`, `host_running`, `wedged`, `status_stale`, `started_at`, `updated_at`, the work-plan counts and the review verdict; every key is always there, and a time is RFC 3339 or `""` when it is not known. A name that is not in the project answers 404 with an `error` sentence. The status POST takes a body of `{"status": "pending", "replaced_by": [], "confirm": true}` with `Content-Type: application/json`, or the form fields `status`, `replaced_by` and `confirm=yes`; `replaced_by` is a list of ids, and only superseded uses it. Without the confirm it answers 400 with `{"error": ...}` and changes nothing, and the ledger file is the same as before. With it, a change answers 200 with the task as it reads now and a `result` with `outcome` (`changed`, or `already` when the task already has that status), `old`, `new` and `text`, the same sentence the command prints. A refused change (an unknown status, superseded with no ids, an id that is not in the plan) answers 400 with the sentence in `error` and changes nothing. A ledger that cannot be written answers 500 the same way. `GET /api/p/<project>/plan` gives the plan page's data: its existing keys are as they were, and two are new. `status` is the planning status, with `known`, `session`, `damaged`, `mode`, `phase`, `line` (the plan line in words), `approvable` and `problems`. `approve` is `{"available": ..., "reason": ...}`, where `reason` is the sentence saying why the plan cannot be approved and is empty when it can. `POST /api/p/<project>/plan/approve` approves the plan, with the same steps as `afk plan approve`, and it needs the confirm: a body of `{"confirm": true}` with `Content-Type: application/json`, or the form field `confirm=yes`. Without it the POST answers 400 with `{"error": ...}` and changes nothing. With it, every answer has the shape `{"project", "result": {"outcome", "text"}}`: `approved` or `already` answers 200, `refused` (nothing was changed) answers 400, and `failed` answers 500. The project is found among the configured projects and then the plans waiting for approval, and the root is never taken from the request. `GET /api/` is the home page's data: `projects`, `reviews` and `usage` as before, and `rows`, one entry per project in the home page's order. Each row has `name`, `state` (one of `running`, `waiting on you`, `paused`, `stopped`, `held for usage`, `nothing ready`, `finished`, `gone`, `can't read` or `no plan`; the badge on the page uses other words for some of these), `label` and `detail` (the words the dashboard shows), `task`, `title` and `phase` (empty when nothing is running), `done` and `total` (tasks), `open` and `blocking` (inbox items), `plan_waiting` and `needs_owner`. The last one returns the project's open planning session as its messages, with `state` (`none` when no planning session is open, `working`, `waiting_for_text`, `waiting_for_choice`, or `unknown`), the pending `questions` with their options, and a `problem` sentence when the conversation cannot be read. It reads the conversation only while the planning session is running, and it has no page yet. `POST /api/p/<project>/plan/chat` sends the owner's reply into that planning session, the one `afk plan` runs in the project's main checkout, from any dashboard pane or from a script. The body is JSON, either `{"text": "your reply"}` for typed text, `{"other": "your own words"}` for an answer in the owner's own words to one single-select question (sent as the keys that type it into the agent's "Type something." row), or `{"choices": [["an option"], ...]}` with one list of option labels for each question the agent is waiting on, in order. Labels rather than numbers, so a page showing an old question cannot pick the wrong option. Typed text goes in as one message and is sent with enter; a choice is sent as the keys that pick the option in the agent's question dialog. Like `afk attach`, the reply takes the session from any dashboard pane that has it open, and that pane is told it was taken over (see *Showing agent sessions*). A sent reply answers 200 with `{"project", "sent"}`, where `sent` is `text` or `choice` (an own answer counts as `text`). A refused reply sends nothing and answers `{"error", "reason"}`: a plain sentence in `error`, and a short code in `reason` (`no_session`, `not_waiting`, `wrong_kind`, `not_offered`, `bad_reply` or `unsupported`) that a script can branch on. The status codes are: 409 when no planning session is open, the session is still working, the reply is the wrong kind for what the agent waits for, or the agent's question cannot be answered this way; 400 when the reply is not one it can use (both or neither kind, an option that was not offered, the same option twice, the wrong number of answers for the questions, or empty text or an empty own answer); 404 for an unknown project; 415 when the body is not sent as `application/json`; 502 when the session cannot be reached within a few seconds, so nothing was typed and the reply can be sent again. A choice reaches the agent's dialog because the afk plugin registers a `PreToolUse` hook for `AskUserQuestion` (plugin 5.7.4), which makes the agent record the open question where the page can read it. A planning session started before you updated the plugin does not have it, so run `afk plugin install` and start the session again; until then a choice is refused with 409. Typed text works either way. The POST is guarded like every POST: the sign-in cookie, the `Origin` check and the 64 KB limit below all apply. `POST /api/p/<project>/plan/change` starts the same three, and needs the confirm: a body of `{"mode": "extend", "confirm": true}`, or `{"mode": "amend", "text": "Add a CSV export task.", "confirm": true}` for amend and `{"mode": "reconcile", "text": "docs/design-system.md", "confirm": true}` for reconcile, with `Content-Type: application/json`. Extend takes no text, and any text sent with it is ignored. Without the confirm it answers 400 with `{"error": ...}` and changes nothing. With it, every answer has `project`, `mode`, `outcome`, `text`, `chat` (the address of the project's planning chat), `session_open`, `open_mode` and `open_phase`. A start or resume answers 200 with `outcome` `started` or `resumed`. A refusal answers 400 with `outcome` `refused`, a plain sentence in `error`, and `reason`: `session_open` when a planning session is already open (then `session_open` is true and `open_mode` and `open_phase` say which), `bad_request` for an unknown mode, a blank amend sentence or reconcile path, text longer than 5000 characters, or a body that cannot be read, and `refused` for any other refusal, such as a project with no plan. A refused change starts nothing. The POST is guarded like every POST: the sign-in cookie, the `Origin` check and the 64 KB limit apply. `POST /api/projects/add` and `POST /api/projects/remove` are the twins of the add and remove pages (see the web page section). Add takes `{"folder": "~/code/shop", "name": "", "confirm": true}`, where an empty `name` uses the folder's own name, and Remove takes `{"name": "shop", "confirm": true}`, both with `Content-Type: application/json`, or the form fields `folder`, `name` and `confirm=yes`. Remove takes the name only and looks it up in the daemon's list, so a folder in the request is never used; a name that is not listed answers 400 with outcome `not_listed` and changes nothing. Without the confirm a POST answers 400 with `{"error": ..., "reason": "confirm_required"}` and changes nothing. With it, every answer has the shape `{"result": {"outcome", "name", "root", "text"}, "pending": ...}`, where `outcome` is `added`, `already`, `removed`, `not_listed`, `refused` or `failed`, `text` is the sentence the page shows, and `pending` is `true` when the change is recorded for the overview's notice. `added`, `already` and `removed` answer 200, `refused` and `not_listed` answer 400, and `failed` answers 500. Only the sign-in cookie opens the API now: there is no `Authorization` header any more. A script uses that cookie: copy the `afk_web` cookie's value from a browser that has signed in, and send it as a `Cookie` header:

```bash
curl -H "Cookie: afk_web=<the value of your browser's afk_web cookie>" http://127.0.0.1:4253/api/p/my-app
```

Every address needs a sign-in, including ones that do not exist: a page with no valid cookie shows the sign-in form, and an `/api` address answers 401 with JSON. A POST whose `Origin` header names another site, or no site at all (`null`), is refused with 403, and a body over 64 KB with 413. The page sends `Referrer-Policy: same-origin`, so your browser tells the page that its own forms are its own, and passes the page's address to no other site. It is not `no-referrer` on purpose: under that policy a browser sends `Origin: null` on every POST, the page's own forms included, and every button on the page would answer 403.

**Links in notifications.** When `public_url` is set (and a password is set, so the page is on), an inbox notification carries a link to the item at `<public_url>/p/<project>/inbox/<id>`. The link holds no password and no cookie. A notification about a planning wait links to the project's planning chat, `<public_url>/p/<project>/plan/chat`, the same way. For a plan waiting for approval that the page does not serve a chat for, it links to the plan page, `<public_url>/p/<project>/plan`. Neither link holds a password or a cookie. A password set while `afk daemon` is running needs a daemon restart before these links open the page, because the page is turned on when the daemon starts. Set `public_url` to the address you use from your phone, without a trailing slash. Its scheme also decides whether the cookie is marked Secure: only an `https://` address does that, so a page used over plain HTTP still works.
