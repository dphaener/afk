# The terminal dashboard

`afk dash` is the full-screen terminal view of afk: every session, its progress, and a live pane of its agent that you can type into. The web page ([web.md](web.md)) does everything the dashboard does except show a session's terminal, so the dashboard is the place to watch an agent work or step in. On a machine you reach over `ssh`, run it in the `ssh` session.

## `afk dash` — Launch the dashboard

Open an interactive TUI dashboard showing afk sessions, their phases, progress, and live diff stats — for the current repo by default, and for every repo discovered under your configured search roots if you have any (see [Multi-project support](#multi-project-support)). Selection preview shows a running session's agent pane. `enter` moves keyboard focus to the right side, and `ctrl+] t` switches that side between the agent and the overview. This is also the default action when you run `afk` with no arguments on a terminal (see [Default action](reference.md#default-action--afk-with-no-arguments)). Unlike earlier versions, `afk dash` does not require being run from inside a git repo — see [Launching outside a repo](#launching-outside-a-repo).

```bash
afk dash [options]
```

**Options:**

- `--interval DURATION` — Refresh interval for session discovery (default `2s`; e.g., `500ms`, `1s`, `5s`). File reads only — never blocks the UI.
- `--open <name>` — Open the named session's embedded pane on start, once the dashboard's first discovery load and first terminal resize have both arrived. The cursor moves to that session, so its pane is the one on screen; the keyboard stays on the list until you press `enter`. If the session's host is not running yet (the usual case immediately after `afk new`), it is restarted first. If the named session isn't found, the dashboard starts normally and shows an error as a toast. This is how `afk new` hands its terminal over.
- `--project PATH` — Launch with `PATH`'s repo as the active project instead of the current working directory's. `~/` is expanded; unlike `new`/`clean`, `dash` does not reject a `PATH` that turns out not to be a git repo — it just starts with no active project, the same [empty state](#launching-outside-a-repo) a launch outside any repo produces. Every other project (the ones in `config.toml`'s project list and any found under the search roots) is still available in the switcher (`p`, below) — this only picks which one starts active.

**Focus.** Keyboard focus is on the session list (left) or on the right side. The right side shows one of two views: the **agent** (the selected session's pane) or the **overview** (the detail pane). The list never controls the right side, whatever it shows. `enter` moves focus to the right side; `ctrl+] \` (or `esc` in the overview) moves it back to the list; `ctrl+] t` switches the view, and only while the right side has focus. A row with no live agent (stopped, pending, worktree fault, cleaning) always shows its overview. `enter` never restarts it; `ctrl+] r` does.

**Keybindings:** The dashboard has two kinds of keys. A few keys for moving around work as they are. Every action goes through one key, the **leader**, `ctrl+]`: press it, then the action's key. Because the leader is the only chord the dashboard claims, the agent pane passes every other key to the agent, so nothing you type in a pane is taken by the dashboard. Press `ctrl+] ?` for the full list in-app, or press `ctrl+]` and type to search the actions by name.

**Moving around** (no leader needed):

- `↑/k`, `↓/j` — Move the selection up and down on the list.
- `pgup`/`pgdn`, `home`/`end` — Page the list, or jump to its first or last session.
- `enter` — Move keyboard focus to the right side (see below).
- `esc` — Close the full help, then clear an applied filter; from the overview, give the keyboard back to the list.
- `tab`/`shift+tab`, `1`–`6` — Switch the detail pane's tab (overview focused).
- Scroll keys (`↑/k`, `↓/j`, `ctrl+u`/`ctrl+d`, `pgup`/`pgdn`, `home`/`end`) and the mouse wheel — Scroll the detail pane (overview focused).
- `ctrl+c` — Quit from the session list or the overview, so a stuck dashboard can always be left. In the agent pane it goes to the agent.

**The leader** (`ctrl+]`, then the key). `ctrl+]` is its own byte (0x1D), so no other key shares it. It replaced Ctrl+Space because Raycast on macOS takes Ctrl+Space, and because tmux's default prefix is `ctrl+b`, so `ctrl+]` passes through tmux untouched. Ctrl+Space, `ctrl+@` and `ctrl+2` all send the same NUL byte; they open nothing now, and in the agent pane they reach the agent as that one NUL like any other key.

**Changing the leader.** `ctrl+]` is the default. To use another key, set `leader` in the `[dash]` table of `config.toml` (see [Config file](#config-file)), for example `leader = "ctrl+o"`. Every hint, help line and the actions dialog then names the key you chose, and the agent pane passes that key on when you press it twice. The setting is read when `afk dash` starts, so restart the dashboard after you change it. The rest of this README names `ctrl+]`, the default.

A value the dashboard cannot use falls back to `ctrl+]`, and the header shows one line that says what is wrong and where to fix it, such as `leader "enter" not used (the dashboard uses it): set e.g. leader = "ctrl+o" in [dash] of config.toml · using ctrl+]`. A value is refused when it is:

- a key the dashboard keeps for itself: `enter`, `esc`, `tab`, `shift+tab`, `ctrl+c`, the movement keys (`up`, `down`, `left`, `right`, `pgup`, `pgdown`, `home`, `end`, `k`, `j`, `ctrl+u`, `ctrl+d`);
- a key with no ctrl or alt, such as `q` or `f5`, which would be typed rather than open the actions;
- a name the dashboard would never see: a misspelling, `shift+a` (shift on a letter arrives as the capital letter, so use ctrl or alt with it, like `ctrl+shift+a`), an upper-case letter like `Q`, modifiers out of order (`shift+ctrl+a` is written `ctrl+shift+a`), or a keypad, media or volume key.

A value that is not text in quotes, such as `leader = 5`, is a bad `[dash]` value (see [Config file](#config-file)): the folder search stops and the file is named in a toast, but the leader still falls back to `ctrl+]`.

Some keys send the same byte as another key, so a terminal that does not report them apart cannot tell them from it: `ctrl+m` is Enter, `ctrl+i` is Tab, `ctrl+h` is Backspace and `ctrl+[` is Esc. A leader on one of these works only in a terminal that reports the keys apart (the kitty keyboard protocol, as Ghostty does). Under tmux it needs `set -s extended-keys on` in your tmux configuration as well. In any other terminal the leader never fires, so pick a key that has its own byte.

The letters that used to run these actions on the list (`n o p c r l / b i q f ? P U`) and `:` now do nothing but show a one-line notice naming the key to use instead, for example `n moved: press ctrl+] then n`. The `:` palette is gone; the dialog's own name filter does its job. In the agent pane a chord such as `ctrl+t` or `ctrl+\` now belongs to the agent.

**Plan actions, by name.** The four change sessions in [`afk plan`](reference.md#afk-plan--plan-a-project-with-your-agent) can also be started from the actions dialog. They have no key, so the table above lists them as typed names: press `ctrl+]`, type the name, and press `enter` on the highlighted row.

- **extend the plan** (type `extend`) starts straight away, with nothing to type.
- **amend the plan** (type `amend`) opens a one-line form. Type one sentence about the change and press `enter`. A blank sentence keeps the form open and starts nothing.
- **fix a bug** (type `a bug`) opens a one-line form that asks what is broken. Type one sentence about the bug and press `enter`. The form starts the [`afk plan fix`](reference.md#afk-plan--plan-a-project-with-your-agent) session and opens it in the planning pane; the session reproduces the bug, finds its cause and adds one fix task to the plan. A blank sentence keeps the form open and starts nothing. Type `a bug`, not `fix a bug`: the letter `f` is the focus key, so a typed `fix` moves the keyboard to the pane instead.
- **reconcile the plan with a document** (type `document`) opens a one-line form. Type the document's path inside the project (for example `docs/design-system.md`) and press `enter`. Type `document`, not `reconcile`: the letter `r` is the restart key, so a typed `reconcile` restarts the selected session when it is stopped.
- **start a new plan** (type `start a new plan`) opens a one-line form that asks for a folder or a name, pre-filled with the active project when that project has no plan. A folder that afk makes for a new name is marked trusted in the agent CLI's own settings first, so the planning session opens straight into the conversation instead of stopping at the CLI's "do you trust this folder?" question. If afk cannot record the trust, the session may still wait at that question; answer it in the planning pane or with `afk attach`. A folder you name that already exists is left as it is.
  - **A folder** (a full path, or one starting with `~/`) must exist. A folder that is not a git repository yet is made one, as `afk plan` does. A folder that already has a plan is refused, and the dashboard points you at extend, amend, document or fix instead. An open planning session in that folder is reopened rather than started again.
  - **A name** (no `/` and no `~`) is made into a folder under the `project location` entry in your profile, after a yes/no question that shows the full path (`y` creates it and makes it a git repository; `n` or `esc` creates nothing). A name may use letters, digits, `.`, `_` and `-`, must start with a letter or digit, and may be at most 100 characters. If your profile has no project location, the name is refused and the message says how to set one (`afk profile set "project location" ~/code`) or to type a full path instead. The location folder itself is never created. If a folder with that name already exists, the dashboard offers to plan in it and creates nothing. If making the repository fails part-way, the folder stays on disk, nothing is removed, and no planning session starts; type its full path to plan in it, or remove it yourself.
  - **A GitHub repository, after a name.** Once the folder is made, the dashboard checks that `gh` (the GitHub command) is installed and logged in, then asks whether to make the private repository `<account>/<name>` on GitHub, where the account is the one `gh` is logged in as. `n` or `esc` (the default; `enter` does not answer) makes nothing. `y` makes the repository, always private, and sets it as the folder's `origin`; nothing is pushed. If `gh` is not installed or not logged in, nothing is asked and the notice says so and what to run (`gh auth login`, then `gh repo create --private` in the folder). If GitHub already has a repository with that name, or the create fails, the notice gives the reason and the folder is left as it is. The question is asked every time and only for a folder the dashboard has just made, never for a folder you typed or one that already existed. Planning starts whatever the answer. The outcome is one line at the start of the notice, and it stays at the start of the notice once the planning pane opens. A folder made this way has no commits yet, which the dashboard treats as having no branches yet, not as a failed branch listing.
  - On success the dashboard switches to that project and opens its planning pane.

- **check the plan** (type `errors`) opens a scrollable box titled `Plan check · <plan path>` with a counts line (`3 milestones · 12 tasks · 2 owner tasks · 1 open questions`), then `<plan path>: no problems found` or `<plan path>: 1 error, 2 warnings`, then one finding per line, errors first, worded as `afk plan lint` words them (`docs/PLAN.md:42: error: T1.2: missing Files [rule]`). `↑/↓`, `pgup`/`pgdn`, `home`/`end` scroll and `esc` closes it. The box shows what was read when it opened; open it again to see a newer reading. Type `errors` (or `warnings`, which shares the help line but cannot be typed first because `w` is the resize key). With no plan it shows the notice `There is no plan to check at docs/PLAN.md.` and opens nothing; before the first read it says `The plan has not been read yet; try again in a moment.`

- **approve the plan** (type `approve`) is available only for a new plan that is at review. Otherwise the row is dimmed and says why. Press `enter` and the confirm shows the project, the plan's path and the checker's counts. `y` approves, and `n` or `esc` leaves the plan at review. The steps are the ones `afk plan approve` runs, in the same order, and the commit and push run away from the screen. A plan with one or more errors has no yes: fix them first, and type `errors` to see them. The result is one notice, and a long git error is cut to its first line (run `afk plan approve --project <folder>` for the rest). Approving also ends the planning session: a pane showing it sees it end, and the notice says "The planning session has ended." When the session could not be stopped, the notice says to run `afk clean master-plan --project <folder>` instead; the plan is approved either way.

A refused start shows the reason in the same words the command prints, and nothing is started. When a planning session is already open, the dashboard says which one it is (its mode and phase) and asks whether to open it: `y` opens it, and `n` or `esc` leaves it closed. After a start, the dashboard selects the `master-plan` row and opens its pane, as `enter` does on that row.

- `↑/k`, `↓/j` — Move selection up/down. **Auto-previews the selected running session in its agent pane** as you move (no focus key needed). That's agent view only: with the overview showing, moving the cursor previews nothing, and the overview stays put until you switch views with `ctrl+] t` from the right side. The cursor must settle for 300ms before connecting — so a held key or fast stepping connects only to the row you stop on. Intermediate rows aren't dialed. **This steals the session from any other client attached to it**, including a `afk attach` in another terminal: a host serves exactly one client, and connecting detaches the previous one. Fast browsing is safe (only the settled row connects), but deliberate slow stepping does connect to each row. A **stopped** session isn't restarted by scrolling onto it (cursor movement starts no processes) and shows its detail view instead. While a pane's open, moving onto any row that isn't the paned session shows that row's detail view rather than the previous session's pane. A session being cleaned is never previewed. A preview that fails to connect is completely silent — no error appears from a bare cursor move. The selection wraps: `↑` on the first session lands on the last, and `↓` on the last comes back around to the first.
- `pgup`/`pgdn`, `home`/`end` — Page the session list, or jump to its first/last session. The list windows to the sidebar's height and pages rather than overflowing it, so on a short terminal or with many sessions these are how you reach a row that is off screen. Each one previews the row it lands on, exactly as `↑`/`↓` do. Deliberately narrow keys: bubbles' own defaults for these gestures are `h`/`l`/`f`/`d`/`b`/`u`/`g`/`G`, three of which the dashboard already spends on label, focus-pane and one-off. These don't wrap. `pgup` on the first page stays where it is, and `end` always lands on the last row.
- `ctrl+u`/`ctrl+d`, `↑/k`/`↓/j`, `pgup`/`pgdn`, `home`/`end` (overview focused) — Scroll the detail pane: half a page (`ctrl+u`/`ctrl+d`), one line, one page, or to the top or bottom. These act only after `enter` has focused the overview; from the list the plain keys move the session cursor and `ctrl+u`/`ctrl+d` do nothing. The content scrolls only when it is taller than the pane, and a right-aligned position percentage shows on the pane's last row **only when the content actually overflows**. The offset stays where you left it, so switching back to the overview picks up where you were.
- `tab`/`shift+tab`, `1`–`6` (overview focused) — Switch the detail pane's tab: Overview, Waves, Stack, Notes, Diff, and Build when the project has a master plan. `tab` cycles forward and wraps, `shift+tab` goes back, and a digit jumps straight to that position in the strip. The digits index what's actually shown, so in a repo without git-spice (no Stack tab) `3` is Notes. Switching tabs puts the scroll back at the top. Like the scroll keys, these act only while the overview has focus; from the list they do nothing.
- `ctrl+] /` — Filter the session list. Type to narrow it (fuzzy, matching the display label, the on-disk name, and the provider for anything that isn't `claude`, so a labelled session is findable by either and typing `codex` or `opencode` finds those sessions), `enter` applies the filter and hands the keyboard back to the dashboard, `esc` cancels while typing or clears an applied filter afterwards. While a filter is applied every per-session key — `enter`, `ctrl+] c`, `ctrl+] l`, `ctrl+] r` — acts on the filtered selection, and the 2s discovery tick keeps the filter applied rather than dropping it. Switching projects with `ctrl+] p` drops it, since a query written against one project's sessions would silently hide another's. Filtering never connects to a session: the filter prompt moves the selection and every keystroke changes the match set, but no preview is armed while the prompt is open — otherwise typing a search would dial (and steal) whichever session currently matched. Accepting or cancelling the filter previews the row it settled on, as any other selection move does. `ctrl+] x` clears an applied filter, as `esc` does.
- `enter`, `ctrl+] f` — Move keyboard focus to the right side. What happens depends on the view the right side is showing:
  - **Agent view, running session with a pane:** focus that pane. Keys go to the session.
  - **Agent view, running session with no pane yet:** connect the session and focus its pane when it arrives. If you go back to the list (`ctrl+] \`) or switch to the overview while it connects, the pane arrives without taking focus. This is the one case where enter connects. It claims the auto-preview already dialing for that row, so a cursor that has just settled does not race it.
  - **Agent view, row with no live agent** (stopped, pending, worktree fault, cleaning): focus the overview. Enter never restarts a host; `ctrl+] r` does.
  - **Overview view:** focus the overview. Its scroll keys (`↑/k`, `↓/j`, `ctrl+u`/`ctrl+d`, `pgup`/`pgdn`, `home`/`end`), the tab keys and `ctrl+c` work, and the leader opens every action. Every other key is ignored, so a scroll gesture can never open, clean or steal a session.

  A connect that fails hands focus back to the list, where enter retries.
- `ctrl+] t` — Switch the right side between the agent and the overview. It works only while the right side has focus, and it never moves focus. Switching to the agent connects the selected running session if it has no pane yet, the same connect `enter` does. Switching to the overview leaves the pane running behind it, and the pane keeps tracking terminal size. On a row with no live agent it does nothing, because that row always shows its overview. From the list it does nothing. **Note:** the dashboard no longer takes `ctrl+t` from the agent pane, so a Claude Code session watched through a pane keeps its own todo toggle.
- `ctrl+] \` — From the right side, return keyboard focus to the list. The pane or overview stays on screen, and `esc` does the same from the overview. From the list, close the open pane if there is one. The session keeps running in the background either way. `afk attach` still detaches with `ctrl+\`. Closing an unfocused pane is how you clear one that auto-preview opened for you, which matters because `ctrl+] c` won't run while any pane is open.
- `ctrl+] g` — Hand the mouse to your terminal, and press it again to take it back. The help line shows the current state, but only while you're focused into the pane. Inside the creation form and the clean confirmation, where every other key belongs to the dialog, `ctrl+g` itself still toggles it. While either modal is up the toggle still works, but the help line is listing the dialog's keys at that point, so the toast is what tells you where the mouse went.
- `ctrl+] w` — Enter resize mode, which moves the divider between the session list and the main region. Inside it, `h`/`←` and `l`/`→` move the divider one percentage point per press, and `H`/`shift+←` and `L`/`shift+→` move it five. The list, the detail view and the embedded pane re-lay out live on each press. `ctrl+w` again saves the split to the state file, so it's restored on the next launch, and `esc` cancels and restores the width from when you entered. Quitting with `ctrl+c` leaves resize mode without saving, `ctrl+g` still toggles the mouse, and other keys are ignored until you save or cancel. It's unavailable while a session pane is focused, since every key then goes to the session. Press `ctrl+] \` to release the pane first.
- `ctrl+] o` — Create a one-off session. This opens a small provider picker with Claude Code preselected, and every open starts on Claude. `↑`/`k` and `↓`/`j` move the highlight and wrap at both ends. `enter` starts the one-off with the highlighted provider. `esc` cancels and creates nothing. The picker lists every registered provider (`claude`, `codex`, `opencode`) whether or not its CLI is installed, same as the `n` form's Provider selector. A missing CLI shows up in the spawn-error dialog. The one-off gets an auto-generated `scratch-N` name, with no branch, worktree, or plan. Its pane opens on the bare CLI for the chosen provider in the repo root. Disabled with no active project. From a shell, `afk new --scratch --provider codex` (or `opencode`) creates the same kind of one-off directly.
- `ctrl+] p` — Open the project switcher: a filterable list of the projects in `config.toml`'s project list (the ones `afk project add` and `afk plan approve` put there), the project the dashboard was started in, and any found under the search folders. A listed project shows the name `afk project list` shows. Each row showing its session count and an awaiting-input dot. Rows are ordered in three tiers: first, projects with any session awaiting input; second, projects by frequency of opening (most-opened first); third, alphabetically by display name with full path as a tie-break. A project's open count increments when you switch to it from the switcher, launch the dashboard with `--project PATH`, or launch from that project's directory; counts persist in afk's UI state file (see **Selection memory** below for its exact location) alongside the remembered per-project selection. `/` filters by name, `↑/k`/`↓/j` move (wrapping at both ends, same as the session list), `enter` switches the dashboard to the selected project (session list, waves, stack, and diff panels all repoint at it — a no-op if it's already active), and once the incoming project's session list loads, its first session is auto-previewed exactly as a cursor move would preview it (same 300ms settle, same refusals: a stopped session is not restarted, a fault row or a session being cleaned is never previewed). `R` triggers an immediate rescan of the configured search roots and re-reads the project list instead of waiting for the next tick, and `esc` clears an active filter first and only then closes the overlay. Two projects that share a basename (e.g. two checkouts both named `api`) are shown with just enough parent path segments to tell them apart; a project with no such collision shows its bare basename. The footer's help line lists the switcher's keys while it's open. The header's right edge also carries a `ctrl+] p: switch projects` hint whenever more than one project is known.
- `ctrl+] A` — Open the **all projects** screen: one screen for every project the daemon builds, so you can see which of them needs you without switching to each. It replaces the session list and the detail pane while it is open. There is one row for each `[[project]]` in `config.toml`, plus the project the dashboard was started in when it is not listed. Each row shows the project's name, how many tasks are done out of how many (`3/9`, or `-` when it has no tasks), a state word, one sentence on what it is doing or why it is not, how many inbox items it has open and how many of them hold a task up ("3 in inbox, 2 hold a task up"), and "plan waiting for approval" when its plan is on the list of plans waiting for you. The state words are the ones `afk daemon status` uses: `running`, `paused`, `stopped`, `waiting on you` (a task is parked on a question or a decision for you), `held for usage`, `finished`, `nothing ready`, `no plan`, and two for a project afk cannot read: `gone` (the folder in `config.toml` does not exist; fix its path or run `afk project remove`) and `can't read` (a build file in the project is damaged; the row says which). Rows that need you come first: `gone`, `can't read`, `stopped`, `waiting on you`, a blocking inbox item, or a plan waiting for approval. Each group keeps the order of `config.toml`, with the unlisted starting project last. A line at the top says "Nothing needs you" or how many rows do. At 100 columns or more each project is one line; below that it is two (name, progress and counts, then the state and its sentence), and long text is cut with an ellipsis. Keys: `↑/k`, `↓/j`, `pgup`/`pgdn`, `home`/`end` move; `enter` closes the screen and switches the dashboard to that project (on a `gone` or `can't read` row it does not switch and says why); `esc` closes it. `ctrl+] P` and `ctrl+] U` pause and resume the build of the selected row's project, not the one the dashboard is on; the notice names the project, and a `gone` or `no plan` row refuses. Other leader actions are dimmed until you close the screen (`esc`).
- `ctrl+] +` — Put a folder on the daemon's list, the same as `afk project add`. It opens a two-step form. The first step asks *Which folder?*: type the folder's full path, or start it with `~/` (for example `~/code/my-app`). A relative path such as `my-app` is refused with a line under the field, and a blank folder keeps the form open. The form starts with the active project's folder already typed in when that folder is not on the list yet. `enter` goes to the second step, *What should it be called?*: type a name, or leave it blank to use the folder's own name, then `enter` adds it. `esc` on either step adds nothing and says so. The folder must be a git repository, and the same refusals as `afk project add` apply (for example a name that is already taken, or a folder that is not a repository); the notice says why and nothing is written. A folder that is already on the list is not an error: the notice says so and nothing changes. If you are still on this screen when the add finishes, the cursor moves to the new row; a result that arrives after you have closed or reopened the screen is shown as a notice only. Like the other actions here, it works only while this screen is open.
- `ctrl+] -` — Take the selected project off the daemon's list, the same as `afk project remove`. A question asks *Remove <name> (<folder>) from the daemon's list?* and says that the folder, its plan and its sessions are not touched, and that a task which is running is left to finish. `y` removes the project from `config.toml`; `n` or `esc` keeps it, and the notice says nothing was removed. The project's own files are never changed. It needs a row that is on the list: the start-up project, shown here although it has no entry in `config.toml`, is refused with "<name> is not in config.toml, so there is nothing to remove." With no row selected it says so, and with the screen closed it asks you to open it first (`ctrl+] A`). With no project in the list the screen shows the starting project and "No projects are listed in <config.toml path>. Add one with afk project add <folder>."; if `config.toml` cannot be read it keeps the last rows and names the file. The screen only reads files, and only while it is open, once every refresh tick.
- `ctrl+] b` — Show the **Build** tab: every task of the project's master plan and where it stands. It works with or without a session selected, because the build belongs to the project, not to a session. It does nothing when the project has no master plan (a short notice says so). Like the other detail keys it moves keyboard focus to the right side; `esc` brings you back to the list.
- `ctrl+] i` — Open the **inbox** overlay: the things the build loop has put in front of you, such as a question it cannot decide alone. See **Overlays and notices** below for its keys. `ctrl+] b`, `i`, `P` and `U` work from the list and the overview, and from the agent pane by way of the list; they never run while the inbox overlay is open.
- `ctrl+] P` — Pause the project's build, the same as `afk pause`: the daemon starts no new task there. A task that is already running finishes; nothing new starts until you press `ctrl+] U`. It works where `ctrl+] b` works. A short notice says what happened, including when the build was already paused.
- `ctrl+] U` — Resume the project's build, the same as `afk resume`: the daemon may start new tasks again, and a stopped line is cleared too. It works where `ctrl+] P` works, and a short notice says whether the build was resumed, whether only the stop was cleared, or whether there was nothing to resume. Neither action stops a session that is running.
- `ctrl+] R` — The refresh usage action takes a fresh usage reading now, the same as `afk usage --refresh`, and show it in the header. It says "Reading usage…" while the agent's command-line tool is asked, which can take up to a minute; the header changes when the reading lands. A second press while one is still running does nothing but say so, so readings never overlap. The reading is taken from the agent you have as the default, and it is saved to `usage.json` only when it succeeds. A failure is a plain notice: the agent's command-line tool was not found, the agent cannot report its usage, usage could not be read (check that the tool is installed and logged in), or the reading could not be saved. In every failure the header keeps the old reading. It works from the list and the overview, and is dimmed over the all-projects screen.
- `ctrl+]` — The leader itself opens the **actions dialog**: a list of every dashboard action with its key and a line saying what it does. It works from the session list, the overview and the agent pane alike, and does nothing while an overlay, a form or a confirmation is open (the inbox, the project switcher, `ctrl+] n`, `ctrl+] l`, `ctrl+] c`, a restart confirmation, the filter prompt, resize mode). Inside the dialog:
  - Press an action's key and it runs once, and the dialog closes. Pressing it from the agent pane moves the keyboard to the list first, so nothing you pick is ever typed to the agent (the few that belong to the right side, `t` and `g`, leave the keyboard there).
  - Type letters that are not an action's key to filter the list by name or help text, `↑`/`↓` move the highlight and `enter` runs the highlighted row.
  - `esc` closes the dialog and sends nothing to the agent.
  - `ctrl+]` a second time closes the dialog. If the agent pane had the keyboard, it also sends ctrl+] to the agent, so the chord is not lost to a program that uses it.
  - `ctrl+]` is the default leader. If `leader` in `[dash]` of `config.toml` sets another key, that key does everything `ctrl+]` does here, and every `ctrl+]` in this list reads as that key. See **Changing the leader** under Keybindings above.
  - An action that cannot run where you are (for example `c` while a pane is open, or `b` in a project with no master plan) is dimmed and says why. Its key and `enter` do nothing and the dialog stays open.



- `ctrl+] ?` — Toggle full help. The help line at the bottom normally shows a curated, width-budgeted subset of keys; `?` expands it to every key that acts on the list, with the leader's actions listed as `ctrl+] X` — and collapses it back on a second press. An action that's currently a no-op for the selection (e.g. `ctrl+] r` with nothing wedged) drops out of both views automatically rather than being listed disabled.
- `ctrl+] n` — Open the in-TUI session-creation form: three fields (name, description, base branch), an `[ ] Autonomous` checkbox below the base list, and a `Provider: ‹ claude ›` selector below that. Tab cycles focus forward through all five; Shift+Tab cycles backward. `space` toggles the checkbox while it has focus (`[x] Autonomous` when on); it types a literal space in the name and description fields and does nothing on the base list. On the Provider selector, `space` or `→` goes to the next provider and `←` to the previous, cycling through `claude`, `codex`, and `opencode` and wrapping at either end. Picking `codex` ticks Autonomous for you, since Codex sessions are autonomous-only. If you untick it and leave `codex` selected, submit fails inline with the same refusal `afk new` gives (`afk new: --provider codex requires --autonomous or --scratch: Codex sessions run autonomous-only`) and nothing gets created. Checked, the form passes `--autonomous` to [`afk new`](reference.md#afk-new--create-a-new-session), and a non-default provider adds `--provider <name>` after it (`opencode` sessions can be interactive or autonomous). Enter submits from name, base, the checkbox, or the selector, and inserts a newline in the description field. `/` starts filtering the base list inside the form; Esc cancels an active filter before canceling the form. The base-branch list wraps too: `↑` on the first branch lands on the last. Submitting creates the session in the background; the dashboard stays responsive, with a placeholder row standing in until discovery reports the real session. Allowed while a pane is open — the new session gets its own host and does not disturb what you are watching.
- `ctrl+] l` — Edit the display label for the selected session. A single-field prompt lets you rename the session in the dashboard view without changing its on-disk identity — the label is display-only and the directory stays as `.afk/{name}/`. Pressing enter saves, esc cancels. Clear a label by deleting all text and pressing enter. Nothing selected is a no-op.
- `ctrl+] c` — Clean the selected session: every session confirms in the dashboard (no shell-out, no second prompt); the clean then runs in-process. Nothing selected is a no-op. Blocked while a pane is open, since clean can remove the worktree out from under a running session — press `ctrl+] \` to close the pane first (that includes a pane auto-preview opened on its own). Also blocked while a clean of that session is already running.
- `d` — From the clean confirmation modal (after pressing `ctrl+] c`), press `d` to clean **and** delete the session's branch. The branch survives by default; `y` cleans without ever touching it, and only `d` opts in to deletion. A merged branch deletes in a single `d`; an unmerged branch asks for confirmation with a second `d` to prevent accidental loss. No effect on scratch sessions (which have no branch). When a clean deleted the branch, the summary line reports its tip SHA as a recovery handle, and — if the branch was git-spice-tracked — names any upstack branches the delete retargeted so you can restack them deliberately.
- `ctrl+] r` — Restart the selected session's host. It works from the list, the overview and the agent placeholder. A **stopped** host restarts at once. From the list, focus stays on the list. From the right side in the agent view, the agent lands focused when it is back, unless you have moved focus to the list meanwhile; in the overview view it connects behind the overview, one `ctrl+] t` away. A **running** session restarts only if the list already shows it WEDGED — a healthy session ignores the key entirely. A wedged restart confirms first (y/n), since this kills a live, unrecoverable process. On confirm, the dashboard closes any pane it already has open on that session and sends a single restart request to the host; the host runs the signal ladder and resumes the same conversation (`claude --resume`, `codex resume`, or `opencode --standalone -s`, per the session's provider) on a fresh process — the dashboard never touches the child directly. A toast reports the real outcome — restarted (the toast names the provider, e.g. `codex is resuming its conversation`), failed (with the host's reason, e.g. an unusable `status.json`), or merely requested when an older host reports nothing. Confirming also **disconnects any other client attached to that session** (a `afk attach` in another terminal): the request briefly takes the session's single client slot, and the confirmation prompt says so. Press `enter` to reconnect once it is back.
- `ctrl+] q` — Quit immediately, with no confirmation. Closing the pane only **detaches** — the session's host is a separate process, so quitting the dashboard cannot end a session. Reattach with `afk dash` or `afk attach <name>`.

**Selection memory:** The dashboard remembers which session you had selected in each project, restored when you switch back or relaunch the dashboard. State is persisted to `$XDG_STATE_HOME/afk/state.json` (default `~/.local/state/afk/state.json`) and keyed by project path. If a remembered session no longer exists, the cursor falls back to the first row. Pane state (scrolling, detail view) is not remembered.

The same file also stores the sidebar split as `sidebar_pct`, an integer percentage of the terminal width given to the session list. The default is 38, and the value is clamped to 15–85. Whenever the terminal is at least 60 columns wide, the session list keeps at least 30 columns and the main region keeps at least 30. On narrower terminals the session list's 30-column floor wins. A missing or zero `sidebar_pct` means the default. Change it with resize mode (`ctrl+] w`, above), not by editing the file.

**View panels:**

When more than one project is known, every panel below describes the **active** project only, so switch with `ctrl+] p` to look at another. The top bar (the header across the top of the screen) is one row in every state. It puts a `afk Dashboard` badge on the left, the cross-project attention line beside it, and a `p: switch projects` hint on the right, which only appears when more than one project is known. The attention line carries the one thing nothing else on screen can tell you: which *other* projects have sessions waiting on you. It names them while they fit (`● 2 awaiting in gamma · 1 in delta`, in the switcher's own row order) and collapses to a single phrase when they don't (`● 6 awaiting in 4 other projects`, or `● 3 awaiting in 1 other project` when there's just the one). Nothing awaiting elsewhere and it renders nothing at all; there's no `0 awaiting`. The active project's own awaiting sessions aren't in it either, since those already have a dot in the list's flag column a few lines down. These counts come from the ~60s project scan rather than the 2s discovery tick, so they can lag the active project's own list by up to a minute. As the terminal narrows the top bar gives pieces up in one fixed order, weakest first: the `p: switch projects` hint, then the `i: inbox` hint, then the attention line's names (they collapse to the aggregate phrase), then the long usage text (it shrinks to the short form), then the long inbox text (it shrinks to the blocking count alone, so items that only wait to be read leave the row here), then the badge, then the short usage text, then the attention line, then the blocking count. The stale notice is the very last piece to go. One exception: when the switch hint is the only thing on the right half (no usage reading and no open inbox item), the names collapse before the hint goes, as they always have. The badge going before the attention line is deliberate — you can act on an alert, and the badge only tells you what you already know you launched. The blocking count outlasts the badge and both hints because it asks you to act in this project: a task stays stopped until you answer its item, and nothing else on the row says so. When discovery is failing, a `stale · discovery failing 12s` notice sits between the badge and the attention line, and it's the last piece to go as the terminal narrows. The list under it has stopped moving, so you can't trust the other counts on the row either, because the cross-project ones come out of that same discovery pass. It's gone as soon as a pass succeeds. Whatever's left last is the only thing ever truncated, so a project name is never cut mid-word.

The right edge also carries the **inbox segment**, just before the usage text. It counts the open inbox items of the **active** project, the same items the Build tab's summary line counts, read from the snapshot the dashboard already loads on each refresh. It reads `inbox 3` when three items are open, and `inbox 3 · 2 blocking` when two of them block a task; the blocking part is drawn in the warning colour. It shows nothing when no item is open, and nothing until the first refresh has read the inbox. It does not need a master plan, and inbox files that cannot be read are not counted. Next to it, `ctrl+] i: inbox` names the keys that open the list.

When afk has a usage reading (the last time it checked how much of your plan's allowance is used), the header's right edge also carries a **usage segment**, such as `usage: paused until Thu 15 Oct 15:57 · Week (all models) 91%`. It says what the build loop decided (running, held, paused until a time, or not launching) and shows the tightest usage window, the one closest to its limit. A segment that carries a decision other than "running" is drawn in the warning colour. A reading more than 30 minutes old is marked as stale. As the terminal narrows the usage segment shrinks to a short form (`paused · 91%`) once the switch hint, the inbox hint and the names have gone, outlives the badge, and goes only after that, with the attention line, the blocking count and the stale notice still kept. The header stays one row at every width.

The reading is only taken when you ask for it, never on a timer or at start-up: press `ctrl+]`, then `R` ("refresh usage"), and the header shows `Reading usage…` while the agent's command-line tool is asked. When the new reading lands the header shows its numbers and the decision for them; a failed reading leaves the header on the old reading and says why in a plain notice.

With zero or one known project — the unconfigured default — the header is just the badge, plus the inbox segment when the active project has open items. No attention line, because there's no other project to report on, and no `ctrl+] p: switch projects` hint. No keybinding hints for `ctrl+] o` or `ctrl+] l` either; the actions dialog and `ctrl+] ?` list them (see above).

- **Session list** (left, sidebar when a pane is open) — a table with a caption row: a state glyph (`◐` host running, `○` host stopped, paused or still being created, `✓` done, `✕` failed or BROKEN, `●` ORPHAN), name, `PHASE`, `TASKS` (done/total), and a one-cell flag (`●` awaiting input, `⚠` wedged, `↻` autonomous). The flag cell shows one glyph, by priority: wedged, then awaiting input, then autonomous, so `↻` only appears while the session needs nothing from you and `⚠`/`●` are never hidden by it. Its title strip (the box's first row) carries the active project's name, since the box holds exactly that project's sessions; with no project known it falls back to `Sessions`. Sessions on a non-default provider get a dim tag after the name (` codex`, ` opencode`). When the row's too narrow to fit both, the tag goes and the name stays. Columns fold as the sidebar narrows: below 40 cells the phase abbreviates (`EXEC`, `REVW`, `PLAN`…), below 32 the task count goes, and below 24 only the name and flag remain. An 80-column terminal lands on the abbreviated rung. Everything that used to sit on a second line — progress bar, branch, stale reason, wedged age — is in the detail pane's Overview now. Windowed: it shows as many rows as the sidebar's height allows and pages through the rest (`pgup`/`pgdn`, `home`/`end`); when it does page, the right end of the title strip says which page you're on. `ctrl+] /` filters it, and the line under the captions is reserved for the filter prompt (blank until you open it). Sessions may appear as BROKEN (worktree directory missing) or ORPHAN (worktree present but has no afk session). These fault rows show their fault type in the phase column, are cleanable with `ctrl+] c` (no phase gate), and cannot auto-preview or show an interactive agent pane; `enter` can still focus their rendered detail view. A standalone `/afk:go` session (status.json in the main checkout, no worktree of its own) is **not** a fault: it renders as an ordinary row with a working detail pane and is cleanable with `ctrl+] c`, but `d` is not offered — the session has no branch of its own. Scratch sessions are likewise unaffected. Note that `d` in the clean confirmation of an ORPHAN row offers to delete a branch afk never created — that population includes worktrees created outside afk — so the merge-state line and the unmerged double-confirm are what stand between you and someone else's branch.
- **Embedded pane** (main region, when a session is hosted) — the live conductor's terminal output, rendered by the bundled PTY + terminal-emulator bridge (`internal/termpane`) — an experimental spike component, not production-hardened
- **Detail pane** (main region, when the overview is showing — none is open, or `ctrl+] t` has put the overview over a pane) — the selected session, in tabs (`tab`/`shift+tab`/`1`–`5`, above). The box's top edge names the session and its bottom edge lists the keys that act on it.
  - **Overview** — name (and on-disk name, if labelled), branch → base, phase, loop, updated time, host state, wedged age; an awaiting-input line when the session is blocked on you; progress bar, diff size vs. base, review verdict; a dim `↻ autonomous` tag on the head line for autonomous sessions (shown regardless of the flag-cell priority above), and a dim provider name after it (`codex`, `opencode`) when the session isn't on Claude; the plan's ready work (see below); the branch's path through the stack; and the last three issues. Pretty much what you'd check before deciding whether to open the pane.
  - **Overview task block** — what can start now, derived from the plan's `**Depends on**` lines rather than from a "current wave":
    - `Ready (N)` lists the incomplete tasks whose dependencies are all satisfied, capped at 5 lines then `+N more`. `Ready` includes tasks already in flight, since the plan file does not record which ready task a worker has picked up.
    - `N blocked by failed dependencies` (dim) counts tasks that can never start until a failed dependency is fixed.
    - `Failed (N)` lists `[!]` tasks, capped at 3 lines then `+N more`.
    - When nothing is ready the heading says why: `No tasks ready — waiting on unmet dependencies` while work is still progressing, or `No tasks ready` when every remaining task is blocked by a failure and only a human can unstick it.
    - When nothing is left to start, it is a summary line: `All N tasks complete`, or `X of N complete, Y failed` when every task is terminal but some failed.
    - A plan with no `**Depends on**` lines (legacy) behaves as before: each task depends on every task in the wave below it, a failed (`[!]`) dependency counts as satisfied, and nothing is reported as blocked. A plan that mixes tasks with and without the line is also treated as legacy.
  - **Waves** — the whole plan, every wave and task with its checkbox state. In a plan where every task declares `**Depends on**`, each pending `[ ]` task carries a `← W2.T1, W2.T4` suffix naming its unmet dependencies; completed dependencies are left out, and the suffix is truncated (or dropped) before the title is when the pane is narrow. Legacy and mixed plans show no suffix.
  - **Stack** (git-spice only; the tab isn't there otherwise) — the branch tree with session ownership annotations.
  - **Notes** — the last 10 lines of learnings and issues, and the full review verdict with its findings.
  - **Build** (only when the project has a master plan; last in the strip, so `5` in a plain repo and `6` with git-spice; `ctrl+] b` jumps to it) — about the whole project, not the selected session, so it looks the same whichever session is highlighted. It starts with a summary line (`1/5 done · T1.2: executing`, then whether the loop is paused or stopped and why, and how many inbox items need you), then one row per master-plan task: its id, a status word and its title, with a detail on the right. The status words are `pending` (not started; the detail says `waiting for T1.2` while a dependency is unfinished, `ready` when it can start, and `yours to do` for a task marked as the owner's), `running` (an agent is working on it; the detail names the session and its phase, or `paused for usage until …`), `shipping` (the work is finished and is on its way to merged: `ci running`, a pull request number), `parked` (set aside; `waiting on you: q-3` names the inbox item holding it, and `answered, starting again soon` means you have answered and the loop will pick it up within a few seconds), `done` (with the pull request and commit), `failed` (with the attempt count), and `superseded` (replaced by other tasks). Sessions that were paused for usage read as paused, not as stopped, in the session list too. The tab needs a master plan (set `plan` in `afk.toml`; the default is `docs/PLAN.md`) and reads the ledger the build loop keeps in `.afk/build/ledger.json`. While the right side has the keyboard, a `›` cursor marks one task row; `↑/k` and `↓/j` move it (and the tab scrolls to keep it in view), `pgup`/`pgdn` move it a page, and `home`/`end` jump to the first and last task. The cursor keeps its task across refreshes. `ctrl+] S` sets that task's status: choose a status, give the replacing task ids for `superseded`, and confirm with `y`; the confirm shows the change (for example `T1.3: failed → pending`) and warns when an agent is working on the task. It does what [`afk ledger set`](reference.md#afk-ledger-set--record-a-tasks-status-by-hand) does and refuses in the same words. With the cursor on a task, its row ends with the task's weighted token total (for example `2.9M weighted`) when there is room; it is the first thing dropped as the tab narrows, before the detail and the title. `ctrl+] T` opens the task's tokens as [`afk tokens <task>`](reference.md#afk-tokens--show-how-many-tokens-a-task-used) prints them (a narrower table, without the input, output and cache columns, when the window is narrow), or says `no tokens recorded for this task yet`, or why the ledger could not be read. The dashboard only reads the ledger; `afk tokens --record` stays a command. From this tab, `ctrl+] P` pauses the build and `ctrl+] U` resumes it, the same as `afk pause` and `afk resume`. A short notice says what happened: paused, already paused, resumed, the stop cleared, nothing to resume, or why it did not work. The summary line shows the new state straight away. The summary also carries a **plan line** when the project has a planning session: `plan: extend · rounds · 2 questions have no answer yet`, `plan: plan waiting for your approval` for a new plan at review, `plan: plan approved`, or `plan: amend · finished · the changes are in the plan`. A damaged planning state file is reported as such, not as no session. With no planning session the line is left out. The `master-plan` session's overview shows the same line. The dashboard reads it from files on each refresh and never writes under `.afk/plan/`.
  - **Diff** — the full `git diff` against the base branch for the focused session, structurally coloured (file headers, additions, removals), scrollable with the existing detail-scroll keys, and — like the rest of the detail pane — focusable with `enter` (above) for the full scroll keymap. Tabs are expanded to 4-column stops, and the diff is capped at 2000 lines with an on-screen marker past that. Unfocused sessions show a one-line summary (`+N/-M across K file(s)`) instead. When the diff is loading you'll see `loading diff…`; this resolves within one `--interval` refresh cycle after a tab switch. If the base branch no longer exists, the Diff tab and the Overview tab's `Diff` line both show `base branch '<name>' no longer exists` instead. This occurs when `afk clean --delete-branch` removes a branch that other sessions still record as their base, since `base_branch` is immutable after session creation.

**Overlays and notices.** The project switcher and the new-session form float as centred boxes over the dashboard, so the session list and whatever you had in the main region stay visible around them. The **inbox overlay** (`ctrl+] i`) lists the project's inbox items: `!` marks one that holds a task up, `·` one that is open and `✓` one already answered, with the ones that hold a task up first. `↑/k` and `↓/j` move, `enter` reads the highlighted item, and `esc` (or `ctrl+g`) closes the list. Inside an item you see its title, what kind it is, how long ago it was raised, its body and any numbered options (the agent's recommendation is marked). Type an answer and press `enter` to send it, or type just a number to pick that option: `2` sends the second option's text. An empty answer is not sent and shows a message instead. `esc` clears what you typed, and a second `esc` goes back to the list; `pgup`/`pgdn` scroll a long item. While you type, every key is text, so `q` does not quit. The answer is written to the item's file as answered from the dashboard (`"answered_via": "tui"`), and a task that was parked on it carries on a few seconds later, when the build loop next looks. The first answer is the one kept: if the item was already answered (from here, from `afk inbox answer`, or from the daemon's web page), the stored answer is shown and left alone. If the item's file has gone, you get a plain sentence saying so. This is the only thing the dashboard writes into a project. Confirmations (clean, restart, the failed-create report) and the label editor are dialogs on the same layer, each with its title on the top edge and its keys on the bottom edge; the status bar (the footer) keeps the help line underneath. Status changes appear as toasts — ephemeral notifications in the top-right corner styled by severity (success, warning, error). Background events toast the same way — a session finishing or failing, one starting to await input, a host dying between ticks, a pane taken over by another window or the web page (see *One client per session*), a stack or branch-listing refresh failing. The dashboard also sets the terminal's window title (`afk · api · 2 awaiting input`) and, in terminals that draw one (Ghostty, iTerm2, Windows Terminal), a tab progress bar tracking the fleet's task completion. **Colour themes.** The dashboard has four colour themes: `tide`, `fjord`, `paper` and `phosphor`. Choose one with `theme` in the `[dash]` table of `config.toml` (see [Config file](#config-file)). Left unset, it uses `tide` on a dark terminal and `paper` on a light one, worked out when the dashboard starts. A theme you name is used on either kind of terminal. The theme's background fills the whole screen, and whatever is under an overlay (the switcher, a dialog, the inbox) is dimmed, so the overlay stands out.

**Degradation (missing tools):**

- **git-spice absent**: The Stack tab is hidden (no topology to display), and the Overview shows no stack line.
- **A project's rendezvous directory is unwritable** (e.g. a read-only checkout): that one project simply loses click-to-focus (see [`afk notify`](reference.md#afk-notify--send-a-desktop-notification)) — its sessions still discover, run, and open normally from the switcher or session list, and every other project's click-to-focus is unaffected.
- **No usage reading** (afk has not checked usage yet, or the file is missing): the header shows no usage segment and looks as it always did.
- **No master plan** (no `plan` file, or none at the configured path): there is no Build tab, and `ctrl+] b` shows a notice saying the project has no master plan. `ctrl+] P` and `ctrl+] U` say there is no build to pause or resume. The rest of the dashboard is unchanged.
- **A plan or ledger that cannot be read**: the Build tab is still there and shows the reason in plain words (for example the line of a malformed task heading) instead of the task rows. Inbox files that cannot be read are counted and mentioned, not hidden.
- **Empty inbox**: `ctrl+] i` opens the overlay with the line `Nothing in the inbox.`
- **State file unwritable** (e.g. a read-only filesystem): selection memory and the switcher's open counts both last only for the current run, so the switcher falls back to awaiting-input-then-alphabetical ordering on the next launch; no error is shown.
**Showing agent sessions.** Run as many sessions as you like; the dashboard shows one agent pane at a time. Moving the cursor previews a running session in it while the right side shows the agent view, and `enter` focuses it. Changing the shown session detaches from the outgoing one — its host is a separate process, so it keeps working in the background. Neither moving the cursor nor `enter` restarts anything; only `ctrl+] r` does. If another client takes the session (a `afk attach` in another terminal) or the connection drops while the right side has focus, the agent view shows a placeholder that names the cause, and focus stays on the right. `enter` reconnects. When another window or the web page takes the session, the placeholder and the notice both read `<name> was taken over by another window or the web page; press enter to reopen it`. The placeholder answers only `enter` and the leader (`ctrl+]`, then `t`, `\`, `r` or `g`); every other key is ignored, so typing into a lost session never reaches dashboard actions.

**Mouse.** The dashboard asks your terminal for mouse reporting, and the mouse follows keyboard focus. With the list focused, the right side ignores the mouse, and a left click on it is the same as `enter`. With the right side focused, the wheel and clicks over it reach the session (or the overview's scroll), so a scroll wheel over a session scrolls that session — Claude Code's own scrollback, not your terminal's. Clicks and drags go through too. A click in the list returns focus to the list.

The catch is that your terminal doesn't see click-drag while the dashboard holds the mouse, so its native text selection is unavailable. `ctrl+] g` is the way out: press it and the mouse goes back to the terminal, select what you want, press it again and the pane has it. Nothing detaches either way. The same chord works in `afk attach`.

**One client per session.** A session's host serves exactly **one** connected client. Connecting from a second dashboard (or a `afk attach`) **steals** the session, and the first client is disconnected, and the dashboard says so with a notice in the same words as the placeholder: `<name> was taken over by another window or the web page; press enter to reopen it`. The host does not say who took it, so the notice does not name either one; `enter` on that pane reopens it the same way, and takes the session back. The session itself never notices — it has no idea anyone is watching.

## Multi-project support

The dashboard lists every project you added with `afk project add` (or started with `afk plan approve`), plus the repo you launched it from. Give it search roots in the `[dash]` table of `config.toml` and it discovers every other afk-enabled repo beneath them too, lets you switch between all of them from inside the dashboard (`ctrl+] p`, see [`afk dash`](#afk-dash--launch-the-dashboard)), and no longer needs a repo to launch from at all.

### Listed projects

The projects in the `[[project]]` list of `config.toml` (the file `afk project list` prints) show up in the switcher on their own. Each shows the name `afk project list` shows, and a project that is also found under a search folder or is the one you started in is one row, not two. The list is read again on every scan and when you press `R` in the switcher, so a project you add appears without restarting the dashboard. A listed folder that no longer exists is left out, with no message. If `config.toml` cannot be read (for example it holds invalid TOML), the dashboard keeps the rows it already shows and a toast names the file so you can fix it. The dashboard changes this file only through the all-projects screen's add (`ctrl+] +`) and remove (`ctrl+] -`), which do what `afk project add` and `afk project remove` do. `afk plan approve` also lists a project, once its plan is approved.

A project started from the dashboard with **start a new plan** stays in the switcher for the rest of that run. After a restart it comes back only through `afk dash --project DIR` or a search folder, until `afk plan approve` lists it in the project list.

### Config file

The search folders are set in the `[dash]` table of `config.toml`, the same file as the project list. Location: `$XDG_CONFIG_HOME/afk/config.toml` when that is an absolute path, otherwise `~/.config/afk/config.toml`. A missing file, or a file with no `[dash]` table, is not an error: afk behaves as if every key were at its default. The daemon ignores this table.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `search_roots` | array of strings | `[]` (none) | Folders to scan for other afk projects. `~/` expands to your home folder; a relative folder is taken from the folder `afk dash` was started in, not from the config file's location. |
| `scan_interval` | duration string | `"60s"` | How often the dashboard scans `search_roots` again for new or removed projects, and reads this file again, so an edit to `search_roots` or `max_depth` takes effect within one interval, with no restart. A Go duration such as `"30s"` or `"2m"`, at least `"1s"`: a smaller number could only queue scans on top of each other. |
| `max_depth` | integer | `3` | How many folder levels below a search root the scan goes down before giving up on that branch. At least 1. |
| `leader` | string | `"ctrl+]"` | The key that opens the actions dialog (see **Changing the leader** under Keybindings in [`afk dash`](#afk-dash--launch-the-dashboard)). Read when `afk dash` starts, so a change needs a restart. A key the dashboard cannot use falls back to `ctrl+]` with a header line saying what to fix. |
| `theme` | string | unset: `tide` on a dark terminal, `paper` on a light one | The colour theme: `tide`, `fjord`, `paper` or `phosphor`. Read when `afk dash` starts, so a change needs a restart. A name that is not one of these shows a toast at start that says what to write, and the dashboard uses `tide` even on a light terminal. A value that is not text in quotes, such as `theme = 5`, is a bad `[dash]` value (see [Config file](#config-file)): the folder search stops and the file is named in a toast. |

Example:

```toml
[dash]
search_roots = ["~/ontra", "~/code/side-projects"]
scan_interval = "30s"
max_depth = 4
leader = "ctrl+o"
```

A search root may itself be an afk repo — it registers as exactly that one project, so a single extra project doesn't need a parent directory invented for it just to be discoverable.

**A bad `[dash]` value is not a startup error.** A `scan_interval` that is not a duration or is under `"1s"`, a `max_depth` below 1, or a value of the wrong kind (a word where a number belongs) does not stop `afk dash`, and it does not stop `afk daemon`, `afk project`, `afk usage`, `afk pause` or `afk inbox` either. The folder search does not run, and a toast in the dashboard names the file and the key (for example `dash.scan_interval`) and says what to write instead. The projects in the `[[project]]` list still show, along with the one you started in and anything an earlier search found. Fix the file from inside the running dashboard; the next scan picks it up. A file that is not valid TOML at all is different: the dashboard keeps the rows it shows and a toast names the file, as described under Listed projects.

**The old `config.json`.** Earlier versions kept the search folders in a `config.json` in the same folder. afk no longer reads it. When one is still there, `afk dash` says so once each time it starts: it prints `afk no longer reads <path>.`, says the search settings now live in `config.toml`, and prints the `[dash]` lines to add, built from the old file when it can be read (a value the new file would refuse is left out with a `#` line naming the key). If `config.toml` already has a `[dash]` line, put the new keys under it and do not add a second one. If the old file cannot be read, the notice says so and gives the three keys commented out with their defaults. The text is printed in the terminal before the dashboard opens, so it is still there after you quit, and the dashboard shows a short toast at start that points to it. The same notice shows when `afk new` hands off to the dashboard. Nothing shows when there is no `config.json`. afk changes neither file: delete the old one yourself once the lines are moved.

### Scan bounds

The scan is bounded by three independent limits, all of which matter on a normal `$HOME`:

- **Depth** — capped at `max_depth` levels below each search root.
- **Repo boundaries** — the walk never descends into a directory once it has qualified as a git repo root, so everything inside a checkout (`node_modules`, `vendor`, build output, `.git` itself) is never walked. Linked worktrees under `.claude/worktrees/` are excluded the same way and never appear as their own project.
- **Symlinks** — never followed. A search root that is itself a symlink is resolved once before the walk starts; any symlink the walk encounters while descending is refused outright, never entered.

A directory counts as a project only if it's a git repo root (a main checkout, not a linked worktree) **and** contains a `.afk/` directory.

### Launching outside a repo

`afk` and `afk dash` no longer require a git repo to launch from. With no active project — because you launched outside any repo, or `--project` named something that turned out not to be a git repo, and no configured search root has found anything (yet) — the dashboard opens to an empty state naming the config file to edit and a one-line example, instead of printing usage and exiting 1. It's replaced by the normal view the moment a scan (or a repo you `cd` into and relaunch from) finds a project.
