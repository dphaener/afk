# The terminal dashboard

`afk dash` is the full-screen terminal view of afk: every session, its progress, and a live pane of its agent that you can type into. The web page ([web.md](web.md)) does everything the dashboard does except show a session's terminal, so the dashboard is the place to watch an agent work or step in. On a machine you reach over `ssh`, run it in the `ssh` session.

## `afk dash` — Launch the dashboard

Open an interactive TUI dashboard showing afk sessions, their phases, progress, and live diff stats — for the current repo by default, and for every repo discovered under your configured search roots if you have any (see [Multi-project support](#multi-project-support)). It has three levels, **All projects**, **Project** and **Agent**: `enter` goes in one level and `esc` comes back out. A running session's agent is the third level, a pane over the dimmed Project. This is also the default action when you run `afk` with no arguments on a terminal (see [Default action](reference.md#default-action--afk-with-no-arguments)). Unlike earlier versions, `afk dash` does not require being run from inside a git repo — see [Launching outside a repo](#launching-outside-a-repo).

```bash
afk dash [options]
```

**Options:**

- `--interval DURATION` — Refresh interval for session discovery (default `2s`; e.g., `500ms`, `1s`, `5s`). File reads only — never blocks the UI.
- `--open <name>` — Start in the named session's Agent, with the keyboard in the agent, once the dashboard's first discovery load and first terminal resize have both arrived. If the session's host is not running yet (the usual case immediately after `afk new`), it is restarted first. A session with no host to restart and no agent (pending, or a worktree fault) opens its details instead. `esc` (after the leader) then goes back to Project. If the named session isn't found, the dashboard starts on the project's view (or on All projects when no project is in view) and shows an error as a toast. This is how `afk new` hands its terminal over.
- `--project PATH` — Launch with `PATH`'s repo as the project in view instead of the current working directory's, and start on that project's view (Project, with All projects behind it). `~/` is expanded; unlike `new`/`clean`, `dash` does not reject a `PATH` that turns out not to be a git repo — it just starts on All projects with no project in view, the same [empty state](#launching-outside-a-repo) a launch outside any repo produces. Every other project (the ones in `config.toml`'s project list and any found under the search roots) is still one step away: `esc` goes up to All projects, and `/` opens the jump search.

**Where it starts.** Launched inside a project's repo, the dashboard starts on Project, with All projects one `esc` behind it. Launched anywhere else (no repo, or a `--project` path that is not one), it starts on All projects. `--project PATH` starts on that project's view, and `--open NAME` starts in that session's Agent.

**Levels.** The dashboard has three levels. **All projects** is the home screen: one row per project, so you can see which of them needs you. **Project** is one project, drawn as a box over the dimmed home screen. It has three numbered **sections**: `1 Sessions` (the project's sessions, grouped, with a read-only pane under them), `2 Build` (the master plan's tasks) and `3 Inbox` (the open inbox items). One section has the keyboard at a time; its title strip is drawn in the accent colour. Below 100 columns the box shows only the focused section, so it fits. **Agent** is the selected session's live agent, drawn as a pane over the dimmed Project and one column narrower than the screen at each side on a terminal 100 columns wide or more (below that the pane is full width). That is for a session on afk's own host. A session whose agent runs in Rex has no Agent level here: `enter` does not draw it, and a notice tells you where it runs (see **Agents that run in Rex** below). Under the agent's title strip is a **band**, one line that sums the session up (its phase, task, diff, loop and host, and the next thing that needs you, in any project), and under the terminal is a row of **chips** naming the keys that work in the Agent (`back`, `details`, `mouse`, `ctrl+] ]` for the next thing that needs you, and `ctrl+] ctrl+]` to send the leader itself). The agent is told its size less those two rows, so it is never drawn cropped. The band drops pieces from the right as the screen narrows, and on a very short screen the chips go first and then the band. The band's piece after the phase is the agent's own message (the one it last reported about itself, shown when the agent has sent one), and it is the first piece dropped when there is no room for it, so the phase, the task and the other pieces stay visible longer than it does. **Details** is a pane over the screen for the selected session, opened with `d` from Project or the Agent: 54 columns on the right over the dimmed screen, or the full width below 100 columns. `esc` closes it and puts you back where you opened it, and an agent behind it keeps running. `enter` goes in a level (All projects to the selected project, Project to the selected session's agent). `esc` comes back out one level, and closes an overlay, a form or a question before it goes anywhere. At All projects `esc` has nowhere to go, so it does nothing. Quitting the dashboard or leaving the Agent never ends a session: its host is a separate process.

A row with no live agent (stopped, pending, worktree fault, cleaning) is not drawn as an Agent: `enter` on it opens its details instead, with the keyboard in them. A stopped session's details show a `r restart` chip in the bottom edge, and `r` there restarts the host and opens the agent; a wedged one offers it too, behind the usual confirm, and a pending or cleaning one never does. `enter` never restarts a host; `r` does.

**Keybindings.** At All projects and Project, a key works alone: nothing else can take it, so `n` starts a new session, `c` cleans one and so on. In the Agent every key goes to the agent, so nothing you type there is taken by the dashboard; to use a dashboard key, press the **leader**, `ctrl+]`, then the key. The same key does the same thing at every level, on whatever is in view. Press `?` for the full list in-app, or `:` to search the actions by name.

**Keys that work alone** (All projects and Project):

- `↑/k`, `↓/j`, `pgup`/`pgdn`, `home`/`end` — Move the selection. The list pages to its height and wraps from the last row to the first with `↑`/`↓`; `pgup`/`pgdn` and `home`/`end` do not wrap.
- `enter` — Go in a level. At Project it opens what the focused section has selected: the session's agent under Sessions, the task's details under Build, the item in the inbox under Inbox, which opens the answer screen on that item (see **Overlays and notices** below). A section with nothing selected opens nothing. For a session that runs in Rex, `enter` does not open an agent here: if you are inside Rex and your Rex app is showing that session, afk brings the agent's Rex window forward and the keyboard stays where it was; otherwise a notice says where the agent runs. A session on afk's own host opens its agent as before.
- `esc` — Go back a level, or close what is open (see **Levels**).
- `/` — Open the jump search (see below).
- `]`, `[` — Go to the next or the previous thing that needs you, in any project (see below).
- `:` — Search every action by name, the ones with no key too (see below).
- `i` — Open the inbox.
- `d` — Show the selected session's details, a pane on the right over the dimmed screen with the keyboard on it. It needs a selected session; with none, the status bar says to select one.
- `R` — Read usage now, as `afk usage --refresh` does.
- `?` — Show the keys overlay (see below).
- `q` — Quit, with no confirmation. `ctrl+c` quits too, so a stuck dashboard can always be left.
- `p` — At Project: pause or resume the project's build. At All projects: pause or resume the selected row's project. A paused or stopped project resumes; any other pauses.
- `n` — At All projects: start a new plan. At Project: start a new session.
- `+`, `-` — At All projects: add a project to the daemon's list, or take the selected one off it.
- `a` — Answer the oldest inbox item that blocks a task, at every level. At All projects it is the oldest across every project: the dashboard switches to that project and opens the answer screen on the item. At Project it is the oldest in the project you are in, and in the Agent (press the leader first, `ctrl+] a`) the same, over the Project. If no inbox in that scope holds a task up, a notice says so and nothing switches. Before the inbox has been read, a notice says it is not read yet.
- `o`, `c`, `r`, `l` — At Project: a one-off session, clean, restart the agent, edit the label of the selected session.
- `tab`, `shift+tab`, `1`, `2`, `3` — At Project: move to the next or the previous section, or straight to `1 Sessions`, `2 Build` or `3 Inbox`. `j`/`k` (or `↑`/`↓`) then move inside the focused section.
- `s`, `t` — At Project, with the Build section focused: set the selected task's status, show its details and tokens. Pressed with another section focused, they say so in a notice that names `2` and `tab`.

**The jump search** (`/`). A box that lists every project, every session and every task you can see, to go to any of them. Type letters and the list keeps what matches: the letters must appear in that order, and the ones that matched are underlined. Spaces are ignored, so `w1 t1` finds task `W1.T1`. A task matches on its id or its title, and a session on its name or label. What needs you comes first, then the rest by name. `↑`/`↓` move the highlight and `enter` goes there: a project opens its view, a session opens its agent (or its project view when it has no agent to open), and a task opens its project with the Build section on that task. If nothing matches, the box says so and `enter` does nothing, so you can correct what you typed. `esc` clears what you typed, and closes the box when it is empty; the leader closes it too. Letters always type here, so a key never runs. The box works from what the dashboard already has in memory, so it opens at once and never waits on another project. If there is nothing to list yet (no project is known), `/` says so in a notice instead.

**What needs you: `]` and `[`.** `]` goes to the next thing that needs you and `[` to the previous one, wrapping round at the ends, at every level (in the Agent, press the leader first: `ctrl+] ]`). There are five kinds, in this order inside a project: a session waiting on you, the oldest inbox item that holds a task up, a plan waiting for approval, a broken session, and a project that has gone or cannot be read. Projects come in the order of the home screen (those that need you first, then the order of `config.toml`), so the keys walk the screen from top to bottom. They start from what is in view: the session in the Agent, the selected session at Project, the selected project at All projects. Where you land depends on the kind. A waiting session opens its agent (or its details when no agent is running, as `enter` does). A blocking inbox item opens its project with the answer screen on that item. A plan to approve and a broken session open their project. A project that cannot be opened is selected on All projects, with a notice saying why. When nothing needs you, a notice says so. The keys use only what the dashboard already has in memory, so they never wait on another project; that memory is refreshed about once a minute outside All projects, so a wait raised a moment ago in another project can take up to a minute to count. While the details hold the keyboard hold the keyboard, `tab`/`shift+tab` and the digits `1`–`5` change their tab instead of the section.

**In the Agent.** Every key goes to the agent except the leader. Press `ctrl+]` and the **key strip** appears in the corner of the screen, with the status bar saying it is waiting for an afk key. The next key then does what it does anywhere: `/`, `]`, `[`, `:`, `i`, `d`, `R`, `?`, `q` and `m` (hand the mouse to your terminal, or take it back) run, `esc` goes back to Project, and `ctrl+]` a second time sends one `ctrl+]` to the agent, so the chord is not lost to a program that uses it. Any key the strip does not list closes it and sends nothing, so a mistyped key never reaches the agent. The Project's own keys (`n`, `c`, `r` and the rest) are not on the strip: go back to Project with leader then `esc` first. `ctrl+c` alone goes to the agent.

**Agents that run in Rex.** A session can run its agent inside Rex instead of on afk's own host. Rex draws that agent in its own window, so afk never draws it in the dashboard, and the Agent level is not used for it. What each key does on such a row:

- `enter` (or a click, `ctrl+t`, or a `]`/`[` landing on it) — If you are inside Rex and your Rex app is showing that session, afk brings the agent's window forward in your Rex app, and the dashboard keeps the keyboard where it was. Otherwise a notice says `This agent runs in Rex: open <project> › <session> in Rex.` and the reason after it, for example that you are not inside Rex, or that your Rex app is showing another session. If Rex cannot be reached, the notice says so and still names where the agent runs. Nothing is copied to the clipboard.
- The preview in the Sessions pane never opens the agent for such a row, so it stays quiet.
- `r` (restart) on a stopped Rex-backed row restarts its host as it does for any row. The notice says where the agent runs, instead of connecting to it.
- `d` (details), `c`, `n` and the other keys work on the row as they do on any other.

A session on afk's own host keeps the Agent level exactly as described above. `afk attach` on a Rex-backed session does the same check and prints one line; see [`afk attach`](reference.md#afk-attach--attach-to-a-running-session).

**The actions search** (`:`). A box listing every action with its key and a line saying what it does. Letters always type into its name filter, so a key never runs here; `↑`/`↓` move the highlight and `enter` runs the highlighted row. `esc` closes it, and so does the leader. An action that works at another level is dimmed and says where it works (for example `r` on All projects). An action that cannot run now says why. The plan actions with no key are reached only from here (see **Plan actions, by name**). In the Agent, `:` is on the strip and leaves the keyboard in the agent behind it.

**The keys overlay** (`?`). Every key, level by level (Everywhere, All projects, Project, Agent), built from the same table as the key handling, so it cannot disagree with it. `/` searches it by key or by help text, `j`/`k` scroll, and `esc` closes it. In the Agent it is opened with the leader first, and the keyboard stays in the agent behind it.

**The leader** (`ctrl+]`, then the key). `ctrl+]` is its own byte (0x1D), so no other key shares it. It replaced Ctrl+Space because Raycast on macOS takes Ctrl+Space, and because tmux's default prefix is `ctrl+b`, so `ctrl+]` passes through tmux untouched. Ctrl+Space, `ctrl+@` and `ctrl+2` all send the same NUL byte; they open nothing now, and in the agent pane they reach the agent as that one NUL like any other key.

**Changing the leader.** `ctrl+]` is the default. To use another key, set `leader` in the `[dash]` table of `config.toml` (see [Config file](#config-file)), for example `leader = "ctrl+o"`. Every hint, help line, the key strip and the keys overlay then name the key you chose, and the agent passes that key on when you press it twice. The setting is read when `afk dash` starts, so restart the dashboard after you change it. The rest of this README names `ctrl+]`, the default.

A value the dashboard cannot use falls back to `ctrl+]`, and the header shows one line that says what is wrong and where to fix it, such as `leader "enter" not used (the dashboard uses it): set e.g. leader = "ctrl+o" in [dash] of config.toml · using ctrl+]`. A value is refused when it is:

- a key the dashboard keeps for itself: `enter`, `esc`, `tab`, `shift+tab`, `ctrl+c`, the movement keys (`up`, `down`, `left`, `right`, `pgup`, `pgdown`, `home`, `end`, `k`, `j`, `ctrl+u`, `ctrl+d`);
- a key with no ctrl or alt, such as `q` or `f5`, which would be typed rather than start a key;
- a name the dashboard would never see: a misspelling, `shift+a` (shift on a letter arrives as the capital letter, so use ctrl or alt with it, like `ctrl+shift+a`), an upper-case letter like `Q`, modifiers out of order (`shift+ctrl+a` is written `ctrl+shift+a`), or a keypad, media or volume key.

A value that is not text in quotes, such as `leader = 5`, is a bad `[dash]` value (see [Config file](#config-file)): the folder search stops and the file is named in a toast, but the leader still falls back to `ctrl+]`.

Some keys send the same byte as another key, so a terminal that does not report them apart cannot tell them from it: `ctrl+m` is Enter, `ctrl+i` is Tab, `ctrl+h` is Backspace and `ctrl+[` is Esc. A leader on one of these works only in a terminal that reports the keys apart (the kitty keyboard protocol, as Ghostty does). Under tmux it needs `set -s extended-keys on` in your tmux configuration as well. In any other terminal the leader never fires, so pick a key that has its own byte.

Earlier versions ran every action through the leader at the list, and had a session filter, a resize mode, a Build key and a switch between the agent and the overview. Those are gone, and pressing a retired key does nothing: no notice names a replacement. In the agent a chord such as `ctrl+t` or `ctrl+\` belongs to the agent.

**Plan actions, by name.** The four change sessions in [`afk plan`](reference.md#afk-plan--plan-a-project-with-your-agent) can also be started from the actions search. They have no key, so the table above lists them as typed names: press `:` (in the Agent, the leader and then `:`), type the name, and press `enter` on the highlighted row. Letters always type there, so a name never runs a key.

- **extend the plan** (type `extend`) starts straight away, with nothing to type.
- **amend the plan** (type `amend`) opens a one-line form. Type one sentence about the change and press `enter`. A blank sentence keeps the form open and starts nothing.
- **fix a bug** (type `a bug`) opens a one-line form that asks what is broken. Type one sentence about the bug and press `enter`. The form starts the [`afk plan fix`](reference.md#afk-plan--plan-a-project-with-your-agent) session and opens it in the planning pane; the session reproduces the bug, finds its cause and adds one fix task to the plan. A blank sentence keeps the form open and starts nothing.
- **reconcile the plan with a document** (type `document`) opens a one-line form. Type the document's path inside the project (for example `docs/design-system.md`) and press `enter`.
- **start a new plan** (type `start a new plan`) opens a one-line form that asks for a folder or a name, pre-filled with the active project when that project has no plan. A folder that afk makes for a new name is marked trusted in the agent CLI's own settings first, so the planning session opens straight into the conversation instead of stopping at the CLI's "do you trust this folder?" question. If afk cannot record the trust, the session may still wait at that question; answer it in the planning pane or with `afk attach`. A folder you name that already exists is left as it is.
  - **A folder** (a full path, or one starting with `~/`) must exist. A folder that is not a git repository yet is made one, as `afk plan` does. A folder that already has a plan is refused, and the dashboard points you at extend, amend, document or fix instead. An open planning session in that folder is reopened rather than started again.
  - **A name** (no `/` and no `~`) is made into a folder under the `project location` entry in your profile, after a yes/no question that shows the full path (`y` creates it and makes it a git repository; `n` or `esc` creates nothing). A name may use letters, digits, `.`, `_` and `-`, must start with a letter or digit, and may be at most 100 characters. If your profile has no project location, the name is refused and the message says how to set one (`afk profile set "project location" ~/code`) or to type a full path instead. The location folder itself is never created. If a folder with that name already exists, the dashboard offers to plan in it and creates nothing. If making the repository fails part-way, the folder stays on disk, nothing is removed, and no planning session starts; type its full path to plan in it, or remove it yourself.
  - **A GitHub repository, after a name.** Once the folder is made, the dashboard checks that `gh` (the GitHub command) is installed and logged in, then asks whether to make the private repository `<account>/<name>` on GitHub, where the account is the one `gh` is logged in as. `n` or `esc` (the default; `enter` does not answer) makes nothing. `y` makes the repository, always private, and sets it as the folder's `origin`; nothing is pushed. If `gh` is not installed or not logged in, nothing is asked and the notice says so and what to run (`gh auth login`, then `gh repo create --private` in the folder). If GitHub already has a repository with that name, or the create fails, the notice gives the reason and the folder is left as it is. The question is asked every time and only for a folder the dashboard has just made, never for a folder you typed or one that already existed. Planning starts whatever the answer. The outcome is one line at the start of the notice, and it stays at the start of the notice once the planning pane opens. A folder made this way has no commits yet, which the dashboard treats as having no branches yet, not as a failed branch listing.
  - On success the dashboard switches to that project and opens its planning pane.

- **check the plan** (type `errors`) opens a scrollable box titled `Plan check · <plan path>` with a counts line (`3 milestones · 12 tasks · 2 owner tasks · 1 open questions`), then `<plan path>: no problems found` or `<plan path>: 1 error, 2 warnings`, then one finding per line, errors first, worded as `afk plan lint` words them (`docs/PLAN.md:42: error: T1.2: missing Files [rule]`). `↑/↓`, `pgup`/`pgdn`, `home`/`end` scroll and `esc` closes it. The box shows what was read when it opened; open it again to see a newer reading. Type `errors` or `warnings`. With no plan it shows the notice `There is no plan to check at docs/PLAN.md.` and opens nothing; before the first read it says `The plan has not been read yet; try again in a moment.`

- **approve the plan** (type `approve`) is available only for a new plan that is at review. Otherwise the row is dimmed and says why. Press `enter` and the confirm shows the project, the plan's path and the checker's counts. `y` approves, and `n` or `esc` leaves the plan at review. The steps are the ones `afk plan approve` runs, in the same order, and the commit and push run away from the screen. A plan with one or more errors has no yes: fix them first, and type `errors` to see them. The result is one notice, and a long git error is cut to its first line (run `afk plan approve --project <folder>` for the rest). Approving also ends the planning session: a pane showing it sees it end, and the notice says "The planning session has ended." When the session could not be stopped, the notice says to run `afk clean master-plan --project <folder>` instead; the plan is approved either way.

A refused start shows the reason in the same words the command prints, and nothing is started. When a planning session is already open, the dashboard says which one it is (its mode and phase) and asks whether to open it: `y` opens it, and `n` or `esc` leaves it closed. After a start, the dashboard selects the `master-plan` row and opens its Agent, as `enter` does on that row.

**What the keys do.**

- `enter` at Project — Go in to the selected session's Agent. A running session with a pane opens it with the keyboard in the agent. A running session with no pane yet connects and takes the keyboard when the pane arrives (it claims the preview already dialing for that row). A row with no live agent shows the placeholder; `enter` never restarts a host. A connect that fails hands the keyboard back to the list, where `enter` retries. **Connecting steals the session from any other client attached to it**, including a `afk attach` in another terminal: a host serves exactly one client.
- Moving the selection at Project — A running session is connected in the background after the cursor has settled for 300ms, so `enter` is instant, but its pane is drawn only in the Agent. A stopped session is not restarted by scrolling onto it, and a session being cleaned is never connected.
- `d` — Show the selected session's details, from Project or from the Agent (leader then `d`): the **details overlay**, 54 columns on the right over the dimmed screen, or the full width below 100 columns. It has tabs (`tab`/`shift+tab`, `1`–`5`, see the panels below), and the keyboard is on it. The scroll keys (`↑/k`, `↓/j`, `ctrl+u`/`ctrl+d`, `pgup`/`pgdn`, `home`/`end`) and the mouse wheel scroll it, `r` restarts a stopped session, and `esc` closes it and returns to where it was opened, with an agent behind it still connected. `q` quits, and `:` and `?` open over it and return to it. The project's master plan is not one of its tabs any more: it is the Build section (`2`). It needs a selected session.
- `m` (Agent) — Hand the mouse to your terminal, and press it again to take it back, so you can select text. `afk attach` has its own `ctrl+g` for the same thing.
- `o` — Create a one-off session. This opens a small provider picker with Claude Code preselected, and every open starts on Claude. `↑`/`k` and `↓`/`j` move the highlight and wrap at both ends. `enter` starts the one-off with the highlighted provider. `esc` cancels and creates nothing. The picker lists every registered provider (`claude`, `codex`, `opencode`) whether or not its CLI is installed, same as the `n` form's Provider selector. A missing CLI shows up in the spawn-error dialog. The one-off gets an auto-generated `scratch-N` name, with no branch, worktree, or plan. Its Agent opens on the bare CLI for the chosen provider in the repo root. Disabled with no active project. From a shell, `afk new --scratch --provider codex` (or `opencode`) creates the same kind of one-off directly.
- `/` — Open the jump search; see **The jump search** above. A project's open count, kept in afk's UI state file alongside the remembered per-project selection, still goes up when you open it from the jump search, launch with `--project PATH`, or launch from that project's directory, but the jump search orders by what needs you and then by name, not by count.
- All projects (the home screen; `esc` from a project's view) — One screen for every project the daemon builds, so you can see which of them needs you without switching to each. From the top it is:
  - **The band**: one line of counts. Each group that has a project shows its glyph and count (`need you`, `running`, `quiet`, `finished`); a group with no project is left out. Then `inbox N` for the open items of every project, with `· M blocking` after it when any of them holds a task up (the blocking part is drawn in the colour for things you must act on). Then `usage NN%` with a bar, when the dashboard has a usage reading; with no reading it is left out.
  - **The column heads**: `PROJECT  STATE  TASKS  NOW  LAST 24H  INBOX` at 100 columns or more. Below that the heads are `PROJECT  TASKS  INBOX` and sit over the first line of each project; `LAST 24H` is added there only when the rows have room for it (see the rows below).
  - **Four groups**, in this order, each under a heading with its count: `NEEDS YOU`, `RUNNING`, `QUIET`, `FINISHED`. A project is under NEEDS YOU when a blocking inbox item is open, a plan waits for approval, or it is `gone`, `can't read`, `stopped` or `waiting on you`, whatever else it is doing. Otherwise it is under RUNNING when a task is running, under FINISHED when it is finished, and under QUIET for everything else (`paused`, `held for usage`, `nothing ready`, `no plan`). A group with no project is left out, and its heading is always open. Inside a group, projects keep the order of `config.toml`, with the unlisted starting project last.
  - **Rows**: at 100 columns or more each project is one line: its state's glyph and word, the name, the tasks bar with `done/total` (or `-` with no task list to count), the sentence on what it is doing or why it is not, the `LAST 24H` activity line, and the inbox cell (`2 · 1 blocking`, `plan to approve`, or both). The activity line is 12 cells, one per two hours of the last 24, oldest first, so the last cell is the two hours up to now. Each cell counts the project's decision-log lines in those two hours (the file `.afk/log/decisions.jsonl` that the build loop writes) and draws them as a bar from `▁` (low) to `▇` (high), scaled to the busiest project on the screen. A project with no lines in a two-hour span shows `▁`; a project whose log cannot be read, or that has none yet, shows blank cells. Below 100 columns each project is two lines: the name, the tasks bar and the inbox cell; then the state word and the sentence. The activity line sits on that first line between the tasks bar and the inbox cell, and only when the widest name and inbox leave room for it, so it is shown for every row or for none. When it does not fit, it is left off and the inbox stays. Long text is cut with an ellipsis.
  - **The selected panel**, under a rule that carries the project's name (`─ beta ───`): what the selected project waits on, the question in full, and what answering it unblocks. For a blocking inbox item it shows `Waits on` the item's kind and id, the title and the body, then `Unblocks` the task and its title (the id alone when the plan gave no title). For a plan waiting for approval it shows `Waits on your approval of a new plan.` and `The build starts once it is approved.`. For a `gone`, `can't read`, `stopped` or `waiting on you` project with no item to show, it shows `Waits on you:` and the row's sentence. For a project with nothing waiting it shows `Nothing here waits on you.` and the sentence. The panel takes a third of the pane (at least three lines), and only the question is cut, with `…`, when it does not fit.
  - **This week**: under the panel, a chart of the week's tokens, summed over every listed project's token ledger (`.afk/log/tokens.jsonl`, the `weighted` figure on each line). It has a heading line, `THIS WEEK  5.1M tokens`, with the week's total, and, at the right end of that line, the usage reading (`week 62% · 5-hour 28% · resets Thu 15:57`) when the dashboard has one. Below it are the last seven days, oldest first, one per part of the line: the weekday, a bar scaled to the busiest of those days (a full block for that day), and the day's number. The chart is left out when the screen is too short to keep one project's two lines in the list, since the list comes first; and when the days do not all fit on the width, the oldest go first. Like the activity line, it is read once when the screen starts, again on each project scan (about once a minute), and whenever the set of projects changes, and never on the 2-second refresh. Each log is read only from its last 1 MB, so a long history costs no more than that.
  - **Chips**: the last line names the keys of this level, each as a key and its word: `enter` open project, `a` answer, `p` pause / resume, `n` new plan, `+` add, `-` remove. A chip that does not fit whole is left out, so on a narrow screen the last ones may not show.

  The screen only reads files. `↑/k`, `↓/j`, `pgup`/`pgdn`, `home`/`end` move; `enter` goes in to that project (on a `gone` or `can't read` row it does not and says why). `a` and `p` work alone here, and so do `n`, `+` and `-`.
- `+` — Put a folder on the daemon's list, the same as `afk project add`. It opens a two-step form. The first step asks *Which folder?*: type the folder's full path, or start it with `~/` (for example `~/code/my-app`). A relative path such as `my-app` is refused with a line under the field, and a blank folder keeps the form open. The form starts with the active project's folder already typed in when that folder is not on the list yet. `enter` goes to the second step, *What should it be called?*: type a name, or leave it blank to use the folder's own name, then `enter` adds it. `esc` on either step adds nothing and says so. The folder must be a git repository, and the same refusals as `afk project add` apply (for example a name that is already taken, or a folder that is not a repository); the notice says why and nothing is written. A folder that is already on the list is not an error: the notice says so and nothing changes. If you are still on All projects when the add finishes, the cursor moves to the new row; a result that arrives after you have left is shown as a notice only. It works only at All projects; elsewhere it says "Go back to All projects first (esc)."
- `-` — Take the selected project off the daemon's list, the same as `afk project remove`. A question asks *Remove <name> (<folder>) from the daemon's list?* and says that the folder, its plan and its sessions are not touched, and that a task which is running is left to finish. `y` removes the project from `config.toml`; `n` or `esc` keeps it, and the notice says nothing was removed. The project's own files are never changed. It needs a row that is on the list: the start-up project, shown here although it has no entry in `config.toml`, is refused with "<name> is not in config.toml, so there is nothing to remove." With no row selected it says so. With no project in the list the screen shows the starting project and "No projects are listed in <config.toml path>. Add one with afk project add <folder>."; if `config.toml` cannot be read it keeps the last rows and names the file.
- `i` — Open the **inbox** overlay: the things the build loop has put in front of you, such as a question it cannot decide alone. See **Overlays and notices** below for its keys. It works at every level and never runs while the overlay is open.
- `p` — Pause or resume the project's build, the same as `afk pause` and `afk resume`: when the build is paused or stopped it resumes (the daemon may start new tasks again, and a stopped line is cleared too), and otherwise it pauses (the daemon starts no new task; a task that is already running finishes). A short notice says what happened, including when there was nothing to change. Neither action stops a session that is running.
- `R` — The read usage action takes a fresh usage reading now, the same as `afk usage --refresh`, and shows it in the header. It says "Reading usage…" while the agent's command-line tool is asked, which can take up to a minute; the header changes when the reading lands. A second press while one is still running does nothing but say so, so readings never overlap. The reading is taken from the agent you have as the default, and it is saved to `usage.json` only when it succeeds. A failure is a plain notice: the agent's command-line tool was not found, the agent cannot report its usage, usage could not be read (check that the tool is installed and logged in), or the reading could not be saved. In every failure the header keeps the old reading.
- A key that cannot run where you are says why in a notice instead of doing nothing (for example `r` on a healthy row: "Only a stopped or stuck agent can be restarted.").
- `n` (Project) — Open the in-TUI session-creation form: three fields (name, description, base branch), an `[ ] Autonomous` checkbox below the base list, and a `Provider: ‹ claude ›` selector below that. Tab cycles focus forward through all five; Shift+Tab cycles backward. `space` toggles the checkbox while it has focus (`[x] Autonomous` when on); it types a literal space in the name and description fields and does nothing on the base list. On the Provider selector, `space` or `→` goes to the next provider and `←` to the previous, cycling through `claude`, `codex`, and `opencode` and wrapping at either end. Picking `codex` ticks Autonomous for you, since Codex sessions are autonomous-only. If you untick it and leave `codex` selected, submit fails inline with the same refusal `afk new` gives (`afk new: --provider codex requires --autonomous or --scratch: Codex sessions run autonomous-only`) and nothing gets created. Checked, the form passes `--autonomous` to [`afk new`](reference.md#afk-new--create-a-new-session), and a non-default provider adds `--provider <name>` after it (`opencode` sessions can be interactive or autonomous). Enter submits from name, base, the checkbox, or the selector, and inserts a newline in the description field. `/` starts filtering the base list inside the form; Esc cancels an active filter before canceling the form. The base-branch list wraps too: `↑` on the first branch lands on the last. Submitting creates the session in the background; the dashboard stays responsive, with a placeholder row standing in until discovery reports the real session.
- `l` — Edit the display label for the selected session. A single-field prompt lets you rename the session in the dashboard view without changing its on-disk identity — the label is display-only and the directory stays as `.afk/{name}/`. Pressing enter saves, esc cancels. Clear a label by deleting all text and pressing enter. Nothing selected is a no-op.
- `c` — Clean the selected session: every session confirms in the dashboard (no shell-out, no second prompt); the clean then runs in-process. Nothing selected is a no-op. If the session has a pane open, the question says so and `y` detaches the pane before the clean runs; `n` or `esc` leaves the pane. Blocked while a clean of that session is already running.
- `d` (in the clean question) — Press `d` to clean **and** delete the session's branch. The branch survives by default; `y` cleans without ever touching it, and only `d` opts in to deletion. A merged branch deletes in a single `d`; an unmerged branch asks for confirmation with a second `d` to prevent accidental loss. No effect on scratch sessions (which have no branch). When a clean deleted the branch, the summary line reports its tip SHA as a recovery handle, and — if the branch was git-spice-tracked — names any upstack branches the delete retargeted so you can restack them deliberately.
- `r` — Restart the selected session's host. It works at Project, and on the placeholder in the Agent. A **stopped** host restarts at once, and the agent lands with the keyboard when it is back, unless you have moved away meanwhile. A **running** session restarts only if the list already shows it WEDGED — a healthy session ignores the key. A wedged restart confirms first (y/n), since this kills a live, unrecoverable process. On confirm, the dashboard closes any pane it already has open on that session and sends a single restart request to the host; the host runs the signal ladder and resumes the same conversation (`claude --resume`, `codex resume`, or `opencode --standalone -s`, per the session's provider) on a fresh process — the dashboard never touches the child directly. A toast reports the real outcome — restarted (the toast names the provider, e.g. `codex is resuming its conversation`), failed (with the host's reason, e.g. an unusable `status.json`), or merely requested when an older host reports nothing. Confirming also **disconnects any other client attached to that session** (a `afk attach` in another terminal): the request briefly takes the session's single client slot, and the confirmation prompt says so. Press `enter` to reconnect once it is back.
- `q` — Quit immediately, with no confirmation. Leaving the Agent only **detaches** — the session's host is a separate process, so quitting the dashboard cannot end a session. Reattach with `afk dash` or `afk attach <name>`.

**Selection memory:** The dashboard remembers which session you had selected in each project, restored when you switch back or relaunch the dashboard. State is persisted to `$XDG_STATE_HOME/afk/state.json` (default `~/.local/state/afk/state.json`) and keyed by project path. If a remembered session no longer exists, the cursor falls back to the first row. Pane state (scrolling, detail view) is not remembered.

The same file also stores the sidebar split as `sidebar_pct`, an integer percentage of the terminal width given to the session list. The default is 38, and the value is clamped to 15–85. Whenever the terminal is at least 60 columns wide, the session list keeps at least 30 columns and the main region keeps at least 30. On narrower terminals the session list's 30-column floor wins. A missing or zero `sidebar_pct` means the default. Nothing in the dashboard changes it now that resize mode is gone; the Project's two sides keep their last split.

**View panels:**

When more than one project is known, every panel below describes the **active** project only, so go up to All projects with `esc`, or press `/`, to look at another. The top bar (the header across the top of the screen) is one row in every state. It puts a `afk Dashboard` badge on the left, the cross-project attention line beside it, and a `/: jump` hint on the right, which only appears when more than one project is known. The attention line carries the one thing nothing else on screen can tell you: which *other* projects have something that needs you. It counts all five kinds that `]` walks (a waiting session, a blocking inbox item, a plan to approve, a broken session, a project that has gone or cannot be read). It names the projects while they fit (`● 2 need you in gamma · 1 in delta`, in the order `]` walks them) and collapses to a single phrase when they don't (`● 6 more need you elsewhere`); with one thing it reads `● 1 needs you in gamma`. Nothing needing you elsewhere and it renders nothing at all; there's no `0 need you`. The active project's own waiting sessions aren't in it either, since those already have a dot in the list's flag column a few lines down. At All projects the counts are as fresh as the 2s read; at the other levels they come from the same read run about every 60s, so they can lag by up to a minute. As the terminal narrows the top bar gives pieces up in one fixed order, weakest first: the `/: jump` hint, then the `i: inbox` hint, then the attention line's names (they collapse to the aggregate phrase), then the long usage text (it shrinks to the short form), then the long inbox text (it shrinks to the blocking count alone, so items that only wait to be read leave the row here), then the badge, then the short usage text, then the attention line, then the blocking count. The stale notice is the very last piece to go. One exception: when the switch hint is the only thing on the right half (no usage reading and no open inbox item), the names collapse before the hint goes, as they always have. The badge going before the attention line is deliberate — you can act on an alert, and the badge only tells you what you already know you launched. The blocking count outlasts the badge and both hints because it asks you to act in this project: a task stays stopped until you answer its item, and nothing else on the row says so. When discovery is failing, a `stale · discovery failing 12s` notice sits between the badge and the attention line, and it's the last piece to go as the terminal narrows. The list under it has stopped moving, so you can't trust the other counts on the row either, because the cross-project ones come out of that same discovery pass. It's gone as soon as a pass succeeds. Whatever's left last is the only thing ever truncated, so a project name is never cut mid-word.

The right edge also carries the **inbox segment**, just before the usage text. It counts the open inbox items of the **active** project, the same items the Build section's summary line counts, read from the snapshot the dashboard already loads on each refresh. It reads `inbox 3` when three items are open, and `inbox 3 · 2 blocking` when two of them block a task; the blocking part is drawn in the warning colour. It shows nothing when no item is open, and nothing until the first refresh has read the inbox. It does not need a master plan, and inbox files that cannot be read are not counted. Next to it, `i: inbox` names the key that opens the list (`ctrl+] i` in the Agent).

When afk has a usage reading (the last time it checked how much of your plan's allowance is used), the header's right edge also carries a **usage segment**, such as `usage: paused until Thu 15 Oct 15:57 · Week (all models) 91%`. It says what the build loop decided (running, held, paused until a time, or not launching) and shows the tightest usage window, the one closest to its limit. A segment that carries a decision other than "running" is drawn in the warning colour. A reading more than 30 minutes old is marked as stale. As the terminal narrows the usage segment shrinks to a short form (`paused · 91%`) once the switch hint, the inbox hint and the names have gone, outlives the badge, and goes only after that, with the attention line, the blocking count and the stale notice still kept. The header stays one row at every width.

The reading is only taken when you ask for it, never on a timer or at start-up: press `R` ("read usage"; `ctrl+] R` in the Agent), and the header shows `Reading usage…` while the agent's command-line tool is asked. When the new reading lands the header shows its numbers and the decision for them; a failed reading leaves the header on the old reading and says why in a plain notice.

With zero or one known project — the unconfigured default — the header is just the badge, plus the inbox segment when the active project has open items. No attention line, because there's no other project to report on, and no jump hint. No keybinding hints for `o` or `l` either; the `:` search and `?` list them (see above).

- **Sessions section** (`1 Sessions`) — the project's sessions in three groups under headings: Needs you (awaiting input, a fault, or failed), Working (everything unfinished) and Done. An empty group is not shown, and sessions are in name order inside a group. The right end of a row carries one word: `asks you` when the session waits for an answer, `open it` when its host is running, and nothing otherwise. When the window is wide enough, the row also shows the agent's own message (the one it last reported about itself), dimmed, in the space between the name and the right end. When it does not fit beside `open it`, it takes that word's place, since `open it` is only a hint; `asks you` always stays. A narrow window leaves the message out so the other columns keep their width. Under the rows is a **read-only pane** for the selected session: branch, phase and loop, its task, the question it is waiting on, diff size, review verdict and host. A line with nothing to say is left out. The pane never takes the keyboard; `enter` opens the session's agent. The Project level draws only these sections; the session list described next is no longer drawn there.
- **Session list** (left, sidebar when a pane is open) — a table with a caption row: a state glyph (`◐` host running, `○` host stopped, paused or still being created, `✓` done, `✕` failed or BROKEN, `●` ORPHAN), name, `PHASE`, `TASKS` (done/total), and a one-cell flag (`●` awaiting input, `⚠` wedged, `↻` autonomous). The flag cell shows one glyph, by priority: wedged, then awaiting input, then autonomous, so `↻` only appears while the session needs nothing from you and `⚠`/`●` are never hidden by it. Its title strip (the box's first row) carries the active project's name, since the box holds exactly that project's sessions; with no project known it falls back to `Sessions`. Sessions on a non-default provider get a dim tag after the name (` codex`, ` opencode`). When the row's too narrow to fit both, the tag goes and the name stays. Columns fold as the sidebar narrows: below 40 cells the phase abbreviates (`EXEC`, `REVW`, `PLAN`…), below 32 the task count goes, and below 24 only the name and flag remain. An 80-column terminal lands on the abbreviated rung. Everything that used to sit on a second line — progress bar, branch, stale reason, wedged age — is in the detail pane's Overview now. Windowed: it shows as many rows as the sidebar's height allows and pages through the rest (`pgup`/`pgdn`, `home`/`end`); when it does page, the right end of the title strip says which page you're on. The line under the captions is blank (the session filter is gone; the line stays so the layout does not move). Sessions may appear as BROKEN (worktree directory missing) or ORPHAN (worktree present but has no afk session). These fault rows show their fault type in the phase column, are cleanable with `c` (no phase gate), and cannot auto-preview or show an interactive agent pane; `enter` opens their details. A standalone `/afk:go` session (status.json in the main checkout, no worktree of its own) is **not** a fault: it renders as an ordinary row with a working detail pane and is cleanable with `c`, but `d` is not offered — the session has no branch of its own. Scratch sessions are likewise unaffected. Note that `d` in the clean confirmation of an ORPHAN row offers to delete a branch afk never created — that population includes worktrees created outside afk — so the merge-state line and the unmerged double-confirm are what stand between you and someone else's branch.
- **Agent pane** (the Agent level, when a session is hosted) — the live conductor's terminal output, rendered by the bundled PTY + terminal-emulator bridge (`internal/termpane`) — an experimental spike component, not production-hardened. Only sessions on afk's own host get this pane; a session whose agent runs in Rex shows a notice instead (see **Agents that run in Rex**)
- **Details overlay** (`d`) — the selected session, in tabs (`tab`/`shift+tab`/`1`–`4`, or `1`–`5` when the project has a stack, above), in a pane over the dimmed screen: 54 columns on the right, the full width below 100 columns. The box's top edge names the session; its bottom edge carries `r restart` when the session can be restarted.
  - **Overview** — name (and on-disk name, if labelled), branch → base, phase, loop, updated time, host state, wedged age; an awaiting-input line when the session is blocked on you; progress bar, diff size vs. base, review verdict; a dim `↻ autonomous` tag on the head line for autonomous sessions (shown regardless of the flag-cell priority above), and a dim provider name after it (`codex`, `opencode`) when the session isn't on Claude; the plan's ready work (see below); the branch's path through the stack; and the last three issues. Pretty much what you'd check before deciding whether to open the pane.
  - **Overview task block** — what can start now, derived from the plan's `**Depends on**` lines rather than from a "current wave":
    - `Ready (N)` lists the incomplete tasks whose dependencies are all satisfied, capped at 5 lines then `+N more`. `Ready` includes tasks already in flight, since the plan file does not record which ready task a worker has picked up.
    - `N blocked by failed dependencies` (dim) counts tasks that can never start until a failed dependency is fixed.
    - `Failed (N)` lists `[!]` tasks, capped at 3 lines then `+N more`.
    - When nothing is ready the heading says why: `No tasks ready — waiting on unmet dependencies` while work is still progressing, or `No tasks ready` when every remaining task is blocked by a failure and only a human can unstick it.
    - When nothing is left to start, it is a summary line: `All N tasks complete`, or `X of N complete, Y failed` when every task is terminal but some failed.
    - A plan with no `**Depends on**` lines (legacy) behaves as before: each task depends on every task in the wave below it, a failed (`[!]`) dependency counts as satisfied, and nothing is reported as blocked. A plan that mixes tasks with and without the line is also treated as legacy.
  - **Waves** — the whole plan, every wave and task with its checkbox state. In a plan where every task declares `**Depends on**`, each pending `[ ]` task carries a `← W2.T1, W2.T4` suffix naming its unmet dependencies; completed dependencies are left out, and the suffix is truncated (or dropped) before the title is when the pane is narrow. Legacy and mixed plans show no suffix.
  - **Stack** (git-spice only; the tab isn't there otherwise) — the branch tree with session ownership annotations.
  - **Notes** — the last 10 lines of learnings and issues, and the full review verdict with its findings.
  - **Build section** (`2 Build`; only when the project has a master plan; it is a section of the project view, not a tab of the details) — about the whole project, not the selected session, except for one **linked row**: the task that belongs to the selected session is filled with the strip colour and ends `◂ name`, whichever section has the keyboard. The link comes from the ledger, so a done or parked task keeps the session that ran it. It starts with a summary line (`1/5 done · T1.2: executing`, then whether the loop is paused or stopped and why, and how many inbox items need you), then one row per master-plan task: its id, a status word and its title, with a detail on the right. The status words are `pending` (not started; the detail says `waiting for T1.2` while a dependency is unfinished, `ready` when it can start, and `yours to do` for a task marked as the owner's), `running` (an agent is working on it; the detail names the session and its phase, or `paused for usage until …`), `shipping` (the work is finished and is on its way to merged: `ci running`, a pull request number), `parked` (set aside; `waiting on you: q-3` names the inbox item holding it, and `answered, starting again soon` means you have answered and the loop will pick it up within a few seconds), `done` (with the pull request and commit), `failed` (with the attempt count), and `superseded` (replaced by other tasks). Sessions that were paused for usage read as paused, not as stopped, in the session list too. The section needs a master plan (set `plan` in `afk.toml`; the default is `docs/PLAN.md`) and reads the ledger the build loop keeps in `.afk/build/ledger.json`. While the Build section has the keyboard, a `›` cursor marks one task row; `↑/k` and `↓/j` move it (and the section scrolls to keep it in view), `pgup`/`pgdn` move it a page, and `home`/`end` jump to the first and last task. The cursor keeps its task across refreshes. `s` sets that task's status: choose a status, give the replacing task ids for `superseded`, and confirm with `y`; the confirm shows the change (for example `T1.3: failed → pending`) and warns when an agent is working on the task. It does what [`afk ledger set`](reference.md#afk-ledger-set--record-a-tasks-status-by-hand) does and refuses in the same words. With the cursor on a task, its row ends with the task's weighted token total (for example `2.9M weighted`) when there is room; it is the first thing dropped as the section narrows, before the detail and the title. `t` (or `enter`) opens the task's details, its status, title and detail with the tokens as [`afk tokens <task>`](reference.md#afk-tokens--show-how-many-tokens-a-task-used) prints them (a narrower table, without the input, output and cache columns, when the window is narrow), or says `no tokens recorded for this task yet`, or why the ledger could not be read. The dashboard only reads the ledger; `afk tokens --record` stays a command. From this section, `p` pauses the build or resumes it, the same as `afk pause` and `afk resume`. A short notice says what happened: paused, already paused, resumed, the stop cleared, nothing to resume, or why it did not work. The summary line shows the new state straight away. The summary also carries a **plan line** when the project has a planning session: `plan: extend · rounds · 2 questions have no answer yet`, `plan: plan waiting for your approval` for a new plan at review, `plan: plan approved`, or `plan: amend · finished · the changes are in the plan`. A damaged planning state file is reported as such, not as no session. With no planning session the line is left out. The `master-plan` session's overview shows the same line. The dashboard reads it from files on each refresh and never writes under `.afk/plan/`.
  - **Diff** — the full `git diff` against the base branch for the focused session, structurally coloured (file headers, additions, removals), scrollable with the existing detail-scroll keys, and — like the rest of the detail pane — focusable with `enter` (above) for the full scroll keymap. Tabs are expanded to 4-column stops, and the diff is capped at 2000 lines with an on-screen marker past that. Unfocused sessions show a one-line summary (`+N/-M across K file(s)`) instead. When the diff is loading you'll see `loading diff…`; this resolves within one `--interval` refresh cycle after a tab switch. If the base branch no longer exists, the Diff tab and the Overview tab's `Diff` line both show `base branch '<name>' no longer exists` instead. This occurs when `afk clean --delete-branch` removes a branch that other sessions still record as their base, since `base_branch` is immutable after session creation.

**Overlays and notices.** The jump search and the new-session form float as centred boxes over the dashboard, so the session list and whatever you had in the main region stay visible around them. The `3 Inbox` section has one row per open item; `enter` on it opens the answer screen on that item. The **inbox overlay** (`i`) lists the project's inbox items: `!` marks one that holds a task up, `·` one that is open and `✓` one already answered, with the ones that hold a task up first. `↑/k` and `↓/j` move, `enter` reads the highlighted item, and `esc` (or `ctrl+g`) closes the list. Opening an item (`enter` on the list, on an inbox row, at a `]` or `[` landing, or with `a`) shows the **answer screen**. Its top line is a strip with the project's name and the item's place among the project's open items (`2 of 3`). Under it come the facts (kind, id, the task it holds up, the session that raised it and how long ago), the title on one line, the body, and the agent's assumption when it gave one. Then the **choices**: the options numbered from `1`, the agent's recommendation marked `recommended`, and last **Write my own answer**. Press `1`–`9` to select an option and `enter` to send the selection. The selection starts on the recommended option, or on the first when there is none. `enter` on **Write my own answer** opens a field, where every key is text, `q` included, and `enter` sends what you typed. An item with no options opens straight in the field. Below the choices one line says what happens next: `<task> starts again within a few seconds of your answer`, or `afk carries on within a few seconds of your answer` when the item holds no task, or `Nothing waits on this; afk keeps your answer for the record` when it holds nothing up. While you choose, `↑`/`↓` (or `k`/`j`) go to the previous or next open item of the project, in the order the Inbox section lists them. `pgup`/`pgdn` scroll a long body. An option is sent as its number, so the store reads `2` exactly as `afk inbox answer <id> 2` does, and an own answer is sent as typed. An empty own answer is not sent and shows a message. `esc` in the field goes back to the choices and keeps what you typed, which stays under the choices so you can see what **Write my own answer** will send. `esc` on the choices goes back to the list when you came from it, or closes the inbox when you opened the item straight on. After a sent answer, an item opened from the list goes back to the list, now showing it as answered; an item opened straight on closes, and the dashboard says `Answered <id>.` The answer is written to the item's file as answered from the dashboard (`"answered_via": "tui"`), with the same fields `afk inbox answer` writes, and a task that was parked on it carries on a few seconds later, when the build loop next looks. The first answer is the one kept: if the item was already answered (from here, from `afk inbox answer`, or from the daemon's web page), the stored answer is shown and left alone. If the item's file has gone, you get a plain sentence saying so. This is the only thing the dashboard writes into a project. Confirmations (clean, restart, the failed-create report) and the label editor are dialogs on the same layer, each with its title on the top edge and its keys on the bottom edge; the status bar (the footer) keeps the help line underneath. Status changes appear as toasts — ephemeral notifications in the top-right corner styled by severity (success, warning, error). Background events toast the same way — a session finishing or failing, one starting to await input, a host dying between ticks, a pane taken over by another window or the web page (see *One client per session*), a stack or branch-listing refresh failing. The dashboard also sets the terminal's window title (`afk · api · 2 awaiting input`) and, in terminals that draw one (Ghostty, iTerm2, Windows Terminal), a tab progress bar tracking the fleet's task completion. In a terminal that understands Program status (OSC 7501), such as Rex, the dashboard also reports afk's own status: the tab shows `blocked` with "2 things need you: …" while an inbox item, a plan to approve or a waiting project needs you; an error while a project's line is stopped (or its folder is gone or unreadable); `working` while a task runs; and `idle` otherwise. It also sends one record per project, naming its running task and phase. It sends these only when something changes, clears them when the dashboard quits, and other terminals ignore them. **Colour themes.** The dashboard has four colour themes: `tide`, `fjord`, `paper` and `phosphor`. Choose one with `theme` in the `[dash]` table of `config.toml` (see [Config file](#config-file)). Left unset, it uses `tide` on a dark terminal and `paper` on a light one, worked out when the dashboard starts. A theme you name is used on either kind of terminal. The theme's background fills the whole screen, and whatever is under an overlay (the jump search, a dialog, the inbox) is dimmed, so the overlay stands out.

**Degradation (missing tools):**

- **git-spice absent**: The Stack tab is hidden (no topology to display), and the Overview shows no stack line.
- **A project's rendezvous directory is unwritable** (e.g. a read-only checkout): that one project simply loses click-to-focus (see [`afk notify`](reference.md#afk-notify--send-a-desktop-notification)) — its sessions still discover, run, and open normally from the jump search or session list, and every other project's click-to-focus is unaffected.
- **No usage reading** (afk has not checked usage yet, or the file is missing): the header shows no usage segment and looks as it always did.
- **No master plan** (no `plan` file, or none at the configured path): the Build section says there is no plan, and `p` says there is no build to pause or resume. The rest of the dashboard is unchanged.
- **A plan or ledger that cannot be read**: the Build section is still there and shows the reason in plain words (for example the line of a malformed task heading) instead of the task rows. Inbox files that cannot be read are counted and mentioned, not hidden.
- **Empty inbox**: `i` opens the overlay with the line `Nothing in the inbox.`
- **State file unwritable** (e.g. a read-only filesystem): selection memory and the project open counts both last only for the current run; no error is shown.
**Showing agent sessions.** Run as many sessions as you like; the dashboard shows one agent pane at a time. Moving the cursor connects a running session in the background, and `enter` opens its Agent. Changing the shown session detaches from the outgoing one — its host is a separate process, so it keeps working in the background. Neither moving the cursor nor `enter` restarts anything; only `r` does. If another client takes the session (a `afk attach` in another terminal) or the connection drops while you are in the Agent, the Agent shows a placeholder that names the cause, and you stay in the Agent. `enter` reconnects. When another window or the web page takes the session, the placeholder and the notice both read `<name> was taken over by another window or the web page; press enter to reopen it`. The placeholder answers `enter`, `r` and the leader (`ctrl+]`, then a key on the strip); every other key is ignored, so typing into a lost session never reaches dashboard actions.

**Mouse.** The dashboard asks your terminal for mouse reporting, and the mouse follows keyboard focus. At Project, a left click on a section focuses it and selects the row under the pointer, and the wheel moves the focused section's selection. While the details overlay is open, the wheel over it scrolls it and every other click is ignored. In the Agent, the wheel and clicks over the agent reach the session, so a scroll wheel over a session scrolls that session — Claude Code's own scrollback, not your terminal's. Clicks and drags go through too, and a click outside the agent does not leave it.

The catch is that your terminal doesn't see click-drag while the dashboard holds the mouse, so its native text selection is unavailable. Leader then `m` is the way out: press it and the mouse goes back to the terminal, select what you want, press it again and the agent has it. Nothing detaches either way. The same chord works in `afk attach`.

**One client per session.** A session's host serves exactly **one** connected client. Connecting from a second dashboard (or a `afk attach`) **steals** the session, and the first client is disconnected, and the dashboard says so with a notice in the same words as the placeholder: `<name> was taken over by another window or the web page; press enter to reopen it`. The host does not say who took it, so the notice does not name either one; `enter` on that pane reopens it the same way, and takes the session back. The session itself never notices — it has no idea anyone is watching.

## afk in Rex

If you run afk on a server and sit at a laptop with the Rex app, `afk rex setup` gives Rex's command palette four afk actions. The palette runs on your laptop and talks to the hub (the machine running afk) over Rex. Nothing from the palette runs on the laptop itself except the calls.

Set it up once on the laptop: `afk rex setup --hub LABEL`, add `require("afk")` to Rex's `init.lua`, then `rex config reload` (see [`afk rex setup`](reference.md#afk-rex-setup--add-afk-to-rexs-command-palette)).

| Action | What it does |
|---|---|
| afk: Open the control room | Brings forward the window of the dashboard in the Rex session named `afk`. |
| afk: Go to the next agent that needs you | Looks through the agents' reports; an agent that is blocked on you comes first, then one that hit an error. It brings that agent's window forward and logs its message. |
| afk: Pause the build | Opens a short terminal in the `afk` session that runs `afk pause`. It closes itself when the command finishes; if the command fails at once it stays open so you can read why. |
| afk: Resume the build | The same, running `afk resume`. |

Keys are suggested in comments inside `afk.lua` (ctrl+alt+a, n, p and r) but none is bound. Remove the `--` in front of a `rex.bind` line if you want one.

## Multi-project support

The dashboard lists every project you added with `afk project add` (or started with `afk plan approve`), plus the repo you launched it from. Give it search roots in the `[dash]` table of `config.toml` and it discovers every other afk-enabled repo beneath them too, lets you switch between all of them from inside the dashboard (`/`, see [`afk dash`](#afk-dash--launch-the-dashboard)), and no longer needs a repo to launch from at all.

### Listed projects

The projects in the `[[project]]` list of `config.toml` (the file `afk project list` prints) show up in the jump search and on the home screen on their own. Each shows the name `afk project list` shows, and a project that is also found under a search folder or is the one you started in is one row, not two. The list is read again on every scan, so a project you add appears without restarting the dashboard. A listed folder that no longer exists is left out, with no message. If `config.toml` cannot be read (for example it holds invalid TOML), the dashboard keeps the rows it already shows and a toast names the file so you can fix it. The dashboard changes this file only through the all-projects screen's add (`+`) and remove (`-`), which do what `afk project add` and `afk project remove` do. `afk plan approve` also lists a project, once its plan is approved.

A project started from the dashboard with **start a new plan** stays in the jump search for the rest of that run. After a restart it comes back only through `afk dash --project DIR` or a search folder, until `afk plan approve` lists it in the project list.

### Config file

The search folders are set in the `[dash]` table of `config.toml`, the same file as the project list. Location: `$XDG_CONFIG_HOME/afk/config.toml` when that is an absolute path, otherwise `~/.config/afk/config.toml`. A missing file, or a file with no `[dash]` table, is not an error: afk behaves as if every key were at its default. The daemon ignores this table.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `search_roots` | array of strings | `[]` (none) | Folders to scan for other afk projects. `~/` expands to your home folder; a relative folder is taken from the folder `afk dash` was started in, not from the config file's location. |
| `scan_interval` | duration string | `"60s"` | How often the dashboard scans `search_roots` again for new or removed projects, and reads this file again, so an edit to `search_roots` or `max_depth` takes effect within one interval, with no restart. A Go duration such as `"30s"` or `"2m"`, at least `"1s"`: a smaller number could only queue scans on top of each other. |
| `max_depth` | integer | `3` | How many folder levels below a search root the scan goes down before giving up on that branch. At least 1. |
| `leader` | string | `"ctrl+]"` | The key that, in the Agent, says the next key is a dashboard key (see **Changing the leader** under Keybindings in [`afk dash`](#afk-dash--launch-the-dashboard)). Read when `afk dash` starts, so a change needs a restart. A key the dashboard cannot use falls back to `ctrl+]` with a header line saying what to fix. |
| `theme` | string | unset: `tide` on a dark terminal, `paper` on a light one | The colour theme: `tide`, `fjord`, `paper` or `phosphor`. Read when `afk dash` starts, so a change needs a restart. A name that is not one of these shows a toast at start that says what to write, and the dashboard uses `tide` even on a light terminal. A value that is not text in quotes, such as `theme = 5`, is a bad `[dash]` value (see [Config file](#config-file)): the folder search stops and the file is named in a toast. |

Example:

```toml
[dash]
search_roots = ["~/ontra", "~/code/side-projects"]
scan_interval = "30s"
max_depth = 4
leader = "ctrl+o"
```

A search root may itself be an afk repo — it registers as exactly that one project, so a single extra project doesn't need a parent directory invented for it just to be discoverable.

**A bad `[dash]` value is not a startup error.** A `scan_interval` that is not a duration or is under `"1s"`, a `max_depth` below 1, or a value of the wrong kind (a word where a number belongs) does not stop `afk dash`, and it does not stop `afk daemon`, `afk project`, `afk usage`, `afk pause` or `afk inbox` either. The folder search does not run, and a toast in the dashboard names the file and the key (for example `dash.scan_interval`) and says what to write instead. The projects in the `[[project]]` list still show, along with the one you started in and anything an earlier search found. Fix the file from inside the running dashboard; the next scan picks it up. A file that is not valid TOML at all is different: the dashboard keeps the rows it shows and a toast names the file, as described under Listed projects.

**The old `config.json`.** Earlier versions kept the search folders in a `config.json` in the same folder. afk no longer reads it. When one is still there, `afk dash` says so once each time it starts: it prints `afk no longer reads <path>.`, says the search settings now live in `config.toml`, and prints the `[dash]` lines to add, built from the old file when it can be read (a value the new file would refuse is left out with a `#` line naming the key). If `config.toml` already has a `[dash]` line, put the new keys under it and do not add a second one. If the old file cannot be read, the notice says so and gives the three keys commented out with their defaults. The text is printed in the terminal before the dashboard opens, so it is still there after you quit, and the dashboard shows a short toast at start that points to it. The same notice shows when `afk new` hands off to the dashboard. Nothing shows when there is no `config.json`. afk changes neither file: delete the old one yourself once the lines are moved.

### Scan bounds

The scan is bounded by three independent limits, all of which matter on a normal `$HOME`:

- **Depth** — capped at `max_depth` levels below each search root.
- **Repo boundaries** — the walk never descends into a directory once it has qualified as a git repo root, so everything inside a checkout (`node_modules`, `vendor`, build output, `.git` itself) is never walked. Linked worktrees under `.claude/worktrees/` are excluded the same way and never appear as their own project.
- **Symlinks** — never followed. A search root that is itself a symlink is resolved once before the walk starts; any symlink the walk encounters while descending is refused outright, never entered.

A directory counts as a project only if it's a git repo root (a main checkout, not a linked worktree) **and** contains a `.afk/` directory.

### Launching outside a repo

`afk` and `afk dash` no longer require a git repo to launch from. With no active project — because you launched outside any repo, or `--project` named something that turned out not to be a git repo, and no configured search root has found anything (yet) — the dashboard opens to an empty state naming the config file to edit and a one-line example, instead of printing usage and exiting 1. It's replaced by the normal view the moment a scan (or a repo you `cd` into and relaunch from) finds a project.
